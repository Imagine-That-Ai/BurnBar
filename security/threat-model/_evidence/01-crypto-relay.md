## Controls present
- AEAD payload seal/open = AES-256-GCM via CryptoKit `AES.GCM.seal/open`, key length pinned to 32 bytes — `HermesRelayCrypto.swift:306-330` `sealToBase64`/`openBase64` — strong — random 96-bit nonce supplied by CryptoKit (combined box), AAD authenticated.
- CSPRNG for content keys = `SecRandomCopyBytes(kSecRandomDefault, …)` with `errSecSuccess` check — `HermesRelayCrypto.swift:138-147` `generateSymmetricKeyData` — strong — no fallback path on RNG failure (throws).
- v3 key wrap = RFC 9180 HPKE **Auth mode**, suite `P256_SHA256_AES_GCM_256`, sender-authenticated by static relay key — `HermesRelayCrypto.swift:493-514` `sealKeyV3`, `:524-557` `openKeyV3` — strong — `info = "OpenBurnBar-HermesRelay-HPKE-v3|"‖key_aad` (`:584-588`); `enc`/`wrappedKey` distinct fields.
- v3 open binds the **pinned** sender key, never a wire field — `HermesRelayAuthenticatedRequest.swift:224-246` passes `pinnedPublicKey` into `openKeyV3`; `senderPublicKey` wire field only checked for equality, not trusted as the auth root (`:225-227`) — strong.
- v2 key wrap (legacy) = 2-DH AuthEncap-shaped: `ikm = ECDH(eph,R)‖ECDH(skS,R)`, HKDF-SHA256, `info` binds prefix‖aad‖enc‖pkR‖pkS — `HermesRelayCrypto.swift:439-461` `authenticatedWrappingKey` — moderate — UKS-resistant via kem_context binding; still sender-authenticated.
- AEAD-level domain separation: large set of distinct AAD labels (`request-v3`, `key-v3`, `chunk`, `gatewayEvent[Key]`, `gatewayMessage[Key]`, `gatewayAttachment{Manifest,Body,Key}`, `mediaSealKey`, `controlSealKey`) each prefixed `OpenBurnBar-HermesRelay-v1|` — `HermesRelayCrypto.swift:149-304,590-592` — strong — prevents cross-lane/cross-slot ciphertext relocation (fails GCM tag).
- AAD binds owner+connection+request+operation+senderDevice+peerNode+**counter**+keyID — `HermesRelayCrypto.swift:157-201` `authenticatedRequestAAD`/`authenticatedKeyAAD` — strong — counter is cryptographically bound, not just cache-checked.
- Replay cache = monotonic counter + per-requestID set with TTL, persisted atomically — `HermesRelayAuthenticatedRequest.swift:91-141` `HermesRelayReplayCache.recordFresh` — moderate — `counter > maxCounter` AND unseen requestID; scoped by uid/conn/device/peer/keyID (`:158-172`).
- Trust resolver enforces pinned record fields, `status=="active"`, key length 65, freshness (≤10 min), escrow device `trustState=="trusted"`, platform allowlist, peerNode + Signal-identity binding — `HermesRelaySenderTrustResolver.swift:59-104,29-57` — moderate — multi-factor pin, fail-closed.
- Host advertises v3 only (`gatewayRelayKeyVersionV3` / `relayEncryptionV3`) for the realtime/iroh lane — `HermesRelayHostService.swift:370-371,435-436` — strong — no v1/v2 advertised on this lane.
- Authenticated request opener hard-requires v3 on the realtime/iroh/Firestore request lane — `HermesRelayAuthenticatedRequest.swift:195-208` (`relayKeyVersion == …V3 && relayEncryption == …V3`) else `senderAuthRequired` — strong — fail-closed; no v1/v2 fallback on this lane.
- Reply chunks reuse the request-scoped authenticated key + chunk AAD (sequence,kind) — `HermesRealtimeRelayHostClient.swift:509-519` — strong — reply integrity/confidentiality inherit from the authenticated request key.
- v3 open normalizes all HPKE failures to one typed error AND **re-throws** (no swallow) — `HermesRelayCrypto.swift:548-556` — strong — not catch-and-continue; caller still fails.

## Claims verified against code
- "Confidentiality of every sealed payload against the relay" — Defensible — `sealToBase64`/`openBase64` AES-256-GCM, relay stores ciphertext only — `HermesRelayCrypto.swift:306-330`.
- "Sender authentication: a frame opens only if sealed by holder of the PINNED peer static key" — Defensible (v3 realtime/iroh lane) — `HermesRelayAuthenticatedRequest.swift:224-246` + `openKeyV3` binds pinned sender — note: holds because the opener hard-requires v3 and binds the pinned key.
- "Forward secrecy for the ephemeral leg only; NO PFS for the static leg; NO KCI protection" — Defensible (self-documented limit, matches code) — header `:10-17`; HPKE Auth + static recipient key confirm both limits — `HermesRelayCrypto.swift:484-487`.
- "Migration never downgrades a v2 link / no downgrade" — Partial — realtime/iroh/Firestore-request lane is v3-hard-required (Defensible there); BUT the **gateway message/event lane** still accepts v2 on open (`HermesGatewayAPI.swift:890-897`) and seals v2 when the **server-supplied** client record advertises only v2 (`:1114-1118,1229-1230`; `GatewayEventSealer.swift:199-218`) — a server/relay can force v3→v2 on that lane. v2 is still sender-auth, so this is "force weaker primitive", not "force forgeable/plaintext".
- "Empty HKDF salt is safe because domain-separated info supplies separation" — Defensible — `info` binds version‖aad‖enc‖pkR‖pkS (v2) / version‖aad (v3) — `HermesRelayCrypto.swift:450-454,584-588` — standard HPKE/HKDF practice; salt optional when IKM is a fresh DH secret.
- "Replay resistance from AAD-bound id + record-after-auth cache" — Partial — cache is real and counter-bound (`recordFresh` :123-141); residual: high-water-mark/requestID state lives in a **deletable JSON file** (`:148-156`, persistenceURL) — deleting it resets `maxCounter` to -1 and the requestID set, enabling bounded replay until the legitimate counter advances. Matches CURE53 T-GW-3.
- "Mirrors Python relay_e2ee.py byte-for-byte" — Unknown — `gateway/crypto/relay_e2ee.py` absent from this repo; cross-language parity unverifiable here.
- "v2 closes the anonymous-sender residual on agent→phone replies" — Defensible — `HermesGatewayAPI.swift:892-897` v2 open binds pinned agent key; `:902-908` v3 same — both bind pinned key.

## Threats
- T-CRY-01 — Gateway lane crypto downgrade v3→v2 via server-supplied version advertisement — STRIDE: Tampering/Spoofing-of-policy; Agentic: MITRE ATLAS AML.T0048 (downgrade) — Medium — GatewayEventSealer / HermesGatewayAPI — attack path: hostile/compromised relay or Firestore writer sets the client record `supportsRelayEnvelopeVersions=[2]`/`preferredRelayEnvelopeVersion=2` (`HermesGatewayAPI.swift:1229-1230`), phone then seals phone→agent events with the weaker bespoke 2-DH v2 wrap (`GatewayEventSealer.swift:210-218`); on the reply side phone accepts v2 if wire `relayKeyVersion==2` (`:890-897`) — existing mitigation: v2 is still sender-authenticated and confidential (no forgery/plaintext downgrade), keys TOFU-pinned & immutable — gap: no signed/pinned floor that refuses v2 once v3 was negotiated (no `_emit_version_or_refuse`; CURE53 T-GW-5 confirms it is unmerged) — residual risk: relay forces the older, less-standard primitive; cryptanalytic margin only (no practical break of v2).
- T-CRY-02 — Pi-agent relay request lane has NO sender authentication (v1 ephemeral-static wrap) — STRIDE: Spoofing/Tampering — Medium — PiAgentCloudRelayHostService — attack path: `decryptRelayRequest` opens with `PiAgentRelayCrypto.unwrapSymmetricKey` (no sender key) (`PiAgentCloudRelayHostService.swift:336-340`); anyone able to write `users/{uid}/pi_agent_relay_requests/*` (compromised session, or a relay/server with the recipient's published public key) can mint a ciphertext that opens, since the v1 wrap binds no sender — existing mitigation: Firestore rules scope writes to the owner namespace (`firestore.rules:3161-3163`); confidentiality vs relay holds — gap: no pinned-sender binding, no counter/replay cache on this lane — residual risk: forged/replayed Pi-agent requests within a compromised owner account; relay cannot read but could inject if it can write owner docs.
- T-CRY-03 — Replay high-water-mark stored in a deletable plaintext file — STRIDE: Tampering (anti-replay state) — Low/Medium — HermesRelayReplayCache — attack path: delete `…/HermesRelay/authenticated-request-replay-cache.json` (`HermesRelaySenderTrustResolver.swift:151-158`) → `maxCounter` resets to -1, requestID set cleared → previously-seen authenticated frames (still within their AAD/key validity and counter ≤ old max) replay until counter advances — existing mitigation: counter is AAD-bound (frame must be a real prior frame, not forgeable); TTL prunes requestIDs; local-only file (attacker needs Mac FS access) — gap: no tamper-evidence / monotonic anchor outside the file — residual risk: bounded local replay after FS compromise (matches CURE53 T-GW-3).
- T-CRY-04 — Pinned-key equality compares full bytes non-constant-time; trust freshness window 10 min — LINDDUN/STRIDE: Spoofing (key confusion) — Low — opener/resolver — attack path: `samePublicKey` decodes base64 and uses `==` on `Data` (`HermesRelayAuthenticatedRequest.swift:309-315`); a timing side-channel on a *public* key comparison is not a secret-leak vector (public values), so impact is informational — existing mitigation: compared values are public keys, not secrets; AEAD tag is the real auth gate — gap: none material — residual risk: negligible (recorded for completeness; NOT a real finding).
- T-CRY-05 — KCI / static-leg compromise reads & forges on the affected link — STRIDE: Spoofing/Information disclosure — Low (accepted, documented) — HermesRelayCrypto — attack path: compromise of a recipient static relay key (HPKE Auth shares this bound) lets an attacker decrypt to that recipient and, with the recipient key, impersonate peers toward it — existing mitigation: keys stored in Keychain (ThisDeviceOnly per CURE53), documented non-goal `:13-19`, not exploitable under relay-only model — gap: by design, no double-ratchet/PQXDH (explicitly banned in header) — residual risk: accepted; consistent with stated threat model.

## Gaps / missing controls
- No cryptographic "version floor" on the gateway lane: once v3 capability is observed, nothing refuses a later v2 frame/seal (server controls the advertised version) — `HermesGatewayAPI.swift:1114-1118,890-897`.
- Pi-agent relay lane lacks sender-auth, counter binding, and replay cache entirely — `PiAgentCloudRelayHostService.swift:323-354` (v1 only; no `senderPrivateKey`/`openKeyV3`).
- Anti-replay state durability: high-water-mark is a deletable file; no monotonic hardware/Keychain anchor — `HermesRelayAuthenticatedRequest.swift:148-156`.
- Cross-language parity with the referenced Python `relay_e2ee.py` cannot be checked (file absent); the "byte-for-byte mirror" comments are unverifiable in this repo.

## Overclaims
- Header/comment: "mirror of relay_e2ee.py — keep in sync" and "Mirrors Python … byte for byte" (`HermesRelayCrypto.swift:5,128-131,474,583`) — the Python file is not in this repo, so the parity claim is unverifiable here; should be read as aspirational, not proven.
- Any prose implying the *entire* phone⇄Mac surface is "v3 HPKE Auth E2E with sender authentication" overstates the **gateway** and **Pi-agent** lanes: gateway still seals/opens v2 under server-chosen version (T-CRY-01); Pi-agent lane is v1 ephemeral-static with NO sender auth (T-CRY-02). Sender authentication is proven only on the realtime/iroh/Firestore-request lane that the v3-hard-required opener gates.
- "Forward secrecy" must be qualified: it exists for the ephemeral DH leg ONLY; the static-leg + KCI are explicit non-goals (correctly self-documented at `:10-19`, but easy to over-read as full PFS).

## Crypto/protocol notes
- Primitives are standard CryptoKit (no homegrown AEAD/curve): P-256 ECDH/HPKE, HKDF-SHA256, AES-256-GCM. No AES-CBC, no encrypt-without-MAC, no static IV (GCM nonce is CryptoKit-internal random per seal), no hardcoded keys observed in these files.
- v2 derivation is a *bespoke* HPKE-AuthEncap-shaped 2-DH (not CryptoKit HPKE); v3 uses real CryptoKit `HPKE.Sender/Recipient` Auth mode. v2 remains a live open path on the gateway lane only.
- AAD design is the strongest control here: distinct labels per lane/slot make ciphertext relocation infeasible (GCM tag fails). Counter is AAD-bound, so the replay cache backs—but is not the sole basis for—replay resistance.
- Error handling on the authenticated open paths is fail-closed and typed; no catch-and-continue swallowing of crypto errors in production opens (`openKeyV3` re-throws; openers throw deny reasons).
