## Threats
- T-GW-01 — HTTP gateway has no App Check; auth is bearer+PoP only — Spoofing/STRIDE (Agentic: tool-auth) — Low — `burnBarHermesGateway` onRequest `:1818` (no enforceAppCheck) vs owner callables that set it — attack path: a stolen bearer token replays from any client; PoP requires the pinned Ed25519 private key so token alone is useless. Mitigation: PoP `:845`, rate limit `:1119`. Gap: no device attestation on the HTTP edge (by design — agents/phones are non-Firebase clients). Residual: theft of BOTH bearer + signing key needed; acceptable.
- T-GW-02 — Body-hash binding only covers JSON body, not multipart/raw or header injection — Tampering/STRIDE — Low — `gatewayRequestBodyHash :604` hashes `stableJSONString(requestBody)`; non-JSON bodies hash to the empty-object string — attack path: if any handler consumed a raw/non-JSON body, PoP would not cover it. Existing mitigation: all write handlers read `requestBody()` (JSON) only; attachments upload bytes to Storage out-of-band (sha256 gated at finalize `:507 requireUploadedGatewayAttachments`). Gap: no explicit reject of non-JSON content-type on signed routes. Residual: low; revisit if a raw-body route is added.
- T-GW-03 — PoP nonce store is per-(uid,clientId); a path/body swap under the SAME nonce within 5 min — Tampering/replay — Low — nonce consumed once `:758-771`, but the nonce is consumed by the FIRST request to present it; signature covers method/path/bodyHash so a swapped request fails signature `:755` before nonce write. Residual: none material.
- T-GW-04 — Entitlement check is fired detached (`void entitlementCheck.catch`) before the client doc is validated — Info/DoS — Info — `:823-824` starts entitlement read on `index.uid` before confirming client active; the result is awaited at `:857`. Attack path: a token whose index points at a uid does a wasted entitlement read even when the client is revoked (`:828`). Gap: minor wasted read on revoked tokens; no security impact (revocation still 401s at `:829`). Residual: negligible.
- T-GW-05 — Events list filters targetClientId AFTER fetch and advances cursor past filtered docs — Info disclosure/availability — Low — `:1100-1106`: query is uid-scoped (tenant-safe) but not client-scoped; cross-client targeted events for the same user are filtered in app code, and `nextCursor` is computed over scanned (pre-filter) docs `:1106` so a client never re-reads another client's events. Gap: relies on app-layer filter, not a Firestore where-clause; a query-shape regression could leak same-user other-client events (still same owner). Residual: low (same-tenant only).
- T-GW-06 — Stale-token index deletion is best-effort and racy — Spoofing/availability — Info — `:831-836` deletes `token_index/${tokenHash}` on tokenHash mismatch with `.catch(()=>undefined)`; concurrent rotation could leave a dangling index entry briefly, but the client-doc tokenHash check `:831` is authoritative so a stale index never authorizes. Residual: none.
- T-GW-07 — `bodyHash` supplied by client is what gets signed AND compared — Tampering — Info — `:710 suppliedBodyHash` is both compared to `expectedBodyHash` `:720` and folded into the signed payload `:743`. Correct: signature is over the client's claimed hash, server independently recomputes and equality-checks, so a forged hash fails `:720` and a real hash that mismatches the body fails there too. No gap.
- T-GW-08 — Owner-auth `enqueueHermesGatewayEvent` requires targetClientId and entitlement but body sealing depends on target relayCapable — Info — `:2314-2330`: a legacy non-relay target is rejected (gate false) so phone→agent events are sealed-only in production. No gap at current state.

## Gaps / missing controls
- No content-type allow-list on PoP-signed HTTP routes (T-GW-02): signature integrity assumes JSON body; add an explicit reject of non-JSON on signed write routes for defense-in-depth.
- Events read scoping is app-layer (T-GW-05), not a `where("targetClientId" in [null, clientId])` Firestore constraint; same-tenant only, but a query regression would not be caught by rules.
- HTTP gateway edge has no App Check / device attestation (T-GW-01) — accepted design for non-Firebase agent/phone clients; PoP is the compensating control.
- `client.tokenHash !== tokenHash` comparison at `:831` is a plain `!==` string compare (not constant-time); low risk because both sides are sha256 hex and the index lookup already keyed on the attacker-known hash — not a token-recovery oracle.

## Overclaims
- None material in this domain. Doc/comment prose ("server never sees plaintext", "blind relay") is consistent with the shape-only validators and the always-false plaintext gate. The one nuance to flag: SUPPORTED relay/signal version sets are non-empty (read back-compat) while PRODUCTION write sets gate new writes — comments at `hermesGateway.ts:148-151` correctly call this asymmetry out, so it is NOT an overclaim, but a reviewer skimming only `SUPPORTED_*` could wrongly conclude v4/Signal is writable.

## Crypto / protocol notes
- PoP: Ed25519 over UTF-8 LF-joined fields with a version-tagged domain separator; key is raw 32B wrapped in fixed SPKI DER prefix (`ED25519_SPKI_DER_PREFIX`) for node `createPublicKey` (`:727-735`). Verify via `crypto.verify(null,...)` `:755`.
- Token: sha256(token) only (no HMAC/pepper) — `hermesGateway.ts:498`. Acceptable since the token is a high-entropy random secret (`generateHermesGatewayBearerToken`) and is also PoP-gated; brute force is infeasible and index is hash-keyed.
- Approval action proof: device Signal-identity key signs canonical {uid,deviceId,actionKind,subjectId,approve,nonce,issuedAt,identity...} (`computerUseSecurity.ts:840-854`), max-age + skew bounded `:806-811`, identity must be the trusted-device-pinned key `:818-833`. Strong binding of the human decision to a trusted device.
