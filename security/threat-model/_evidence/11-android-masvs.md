## Claims verified against code
- "All app data excluded from cloud backup & D2D transfer" — Defensible — `AndroidManifest.xml:36`, `data_extraction_rules.xml` (all domains excluded in both blocks) — note: relies on Android 12+ honoring device-transfer rules.
- "Android at-rest Signal sender-auth verified (parity with iOS)" — Defensible — `CloudVaultCrypto.kt:494-555` + caller wiring `AssistantChatHistoryStore.kt:818-833`, `CLIAgentMissionDispatcher.kt:985-999`. (Stale prompt note "no at-rest sender-auth verify" = NOT current.)
- "Phone-control signing key is a biometric/StrongBox hardware identity" — Defensible — `PhoneControlSecureEnclaveKeystore.kt:116-134`; default-ON via Remote Config static-source resolves true `:41-45`.
- "Remote Unlock never persists the Mac password in cleartext; OS-auth required to read" — Defensible — `RemoteUnlockSavedCredentialStore.kt:84-97` + biometric gate before submit `ScreenShareViewerActivityRemoteUnlockSupport.kt:231-242`.
- "Backend traffic can never downgrade to cleartext" — Partial — backend hosts denied (`network_security_config.xml:40-54`) but base-config still `cleartextTrafficPermitted="true"` @33 for LAN-direct; any non-deny-listed host (e.g. a relay/cloudflare host not in list, third-party SDK) can use HTTP. App-layer `validatedBaseURL` is the only gate for those.
- "Device/Signal/relay private keys are protected at rest" — Partial — wrapped by `AndroidLocalSecretBox` Keystore AES-GCM key (`CloudVaultCrypto.kt:1206-1221`) but that key is NOT StrongBox-backed and NOT user-auth-bound; raw key blobs live in plain `SharedPreferences` (`CloudVaultCrypto.kt:1056-1072`, `AndroidSignalIdentityKeyStore.kt:39-57`, `HermesRelayKeyStore.kt:33`). Protection ≈ TEE-wrapped-software-key, not hardware-bound nor screen-lock-gated.
- "StrongBox used for key storage" — Partial/NotDefensible for vault/signal/relay keys — only the phone-control signing key and (implicitly) the Remote Unlock key use Keystore-hardware; `AndroidLocalSecretBox` does not set StrongBox.
- "senderSetComplete reflects whether the full trusted-sender set is resolved" — Partial — heuristic `trustedSenderPublicKeys.size > 1` (`AssistantChatHistoryStore.kt:818`, `CLIAgentMissionDispatcher.kt:985`). A user with exactly one OTHER device, or transient Firestore failure returning only the local key, yields size==1 ⇒ treated as INCOMPLETE ⇒ unknown-sender stays legacy-eligible (downgrade window). See T-AND-04.

## Threats
- T-AND-01 — Vault/Signal/relay private keys recoverable from a rooted/forensic device — Spoofing/Tampering, STRIDE-S/T / MASVS-STORAGE-1,CRYPTO-2 — component: `AndroidLocalSecretBox` + SharedPreferences — attack path: attacker with root or a Keystore-extraction exploit reads `openburnbar_cloud_vault_device`/Signal/relay prefs and unwraps via the non-auth Keystore AES key (no per-use biometric, no StrongBox) → decrypts wrapped vault key → reads all cloud chat — Med severity — existing mitigation: Keystore-wrapped (key non-exportable, survives if TEE holds), allowBackup=false, FLAG_SECURE — gap: key not user-auth-bound/StrongBox; blobs in clear prefs — residual: HIGH on rooted device, LOW on stock locked device.
- T-AND-02 — Base-config cleartext permits HTTP to any non-deny-listed host — Information Disclosure/MITM, STRIDE-I / MASVS-NETWORK-1 — component: `network_security_config.xml:33` — attack path: an SDK, image loader, or relay/tunnel host not in the deny list (or a future code path) issues plain HTTP on a hostile network → traffic interception/injection; only app-layer `validatedBaseURL` blocks public-HTTP and it does not cover all callers — Med — mitigation: backend hosts hard-denied @40-54, app-layer validation — gap: no OS-level LAN-only scoping (cannot express RFC1918 CIDR) — residual: MEDIUM.
- T-AND-03 — Exported deep-link / widget / IME / wallpaper surface — Tampering/EoP, STRIDE-T/E / MASVS-PLATFORM-1 — component: `AndroidManifest.xml` MainActivity exported+BROWSABLE @66-78, widget receivers exported @87-146 (APPWIDGET_UPDATE only), QuickGlanceActivity exported+BROWSABLE @195-205 — attack path: a malicious app fires `burnbar://...` / widget broadcasts → navigate/UI side effects — Low — mitigation: deep-link is navigation-only no auto-submit (`MainActivityIntentActions.kt`), E2E action launchers `BuildConfig.DEBUG`-gated (`MainActivityE2EActions.kt:18,45`, `MainActivityE2EComputerUseActions.kt:13`) and require non-URL boolean extras, widget receivers only consume standard AppWidget broadcasts — gap: deep-link input still parsed in release; no signature-permission on receivers — residual: LOW.
- T-AND-04 — Sender-auth downgrade window while trusted-sender set is "incomplete" — Spoofing/Tampering, STRIDE-S/T / Agentic-supply-chain / MASVS-AUTH — component: `SignalAtRestFallbackPolicy.kt:34-50` + `senderSetComplete = size>1` heuristic — attack path: server/Firestore writer strips senderAuth or supplies an unknown-sender envelope; while `trustedSenderPublicKeys.size==1` (single peer, or Firestore read of escrow_devices failed @ `AndroidCloudVaultSignalPayloads.kt:143`) `SenderNotTrusted` is legacy-eligible (@:42) → recipient decodes the sender-UNauthenticated legacy `sealedPayload` — Med — mitigation: forged-signature & stripped-block ALWAYS fail-closed (@38-40), binding-mismatch fail-closed (@45) — gap: size>1 is a coarse readiness proxy, not a "published set complete" signal; a fetch failure silently downgrades — residual: MEDIUM (narrows to readiness/single-peer cases).
- T-AND-05 — Remote Unlock saved credential readable if device-credential bypass / no fail-closed on load — Info Disclosure, STRIDE-I / MASVS-AUTH-2 — component: `RemoteUnlockSavedCredentialStore.load:47-64` — attack path: `load()` swallows the auth/crypto exception and returns null rather than forcing the prompt; callers MUST invoke `authenticateForRemoteUnlock` first — if a caller path reads the store without the biometric prompt the Keystore still enforces auth (decrypt throws) so the value is not exposed, but absence of an explicit assertion is a footgun — Low — mitigation: Keystore `setUserAuthenticationRequired(true)` makes decrypt require fresh auth regardless of caller — gap: no compile-time coupling between prompt and read — residual: LOW.
- T-AND-06 — Sentry/Crashlytics capture of sensitive in-memory data — Info Disclosure, STRIDE-I / MASVS-PRIVACY — component: `AndroidManifest.xml:49-62` (Sentry DSN, 10% traces, ANR), Crashlytics generated res — attack path: crash/ANR payloads or breadcrumbs include prompt/credential fragments shipped off-device — Low/Info — mitigation: DSN injected only in CI/non-debug, FLAG_SECURE limits screen capture — gap: no evidence of PII scrubbing config reviewed here — residual: LOW (needs Sentry beforeSend config check).

## Gaps / missing controls
- Vault device key, Signal identity key, and Hermes relay key are NOT StrongBox-backed and NOT user-authentication-bound — only software-key-in-TEE wrapping (`CloudVaultCrypto.kt:1206-1221`, `AndroidSignalIdentityKeyStore.kt`, `HermesRelayKeyStore.kt:33`). Parity gap vs the phone-control key which IS StrongBox+biometric.
- Base network config remains cleartext-permitted (`network_security_config.xml:33`); LAN-direct exception not yet migrated to TLS/relay (the file's own "tracked separately" recommendation @26-28 is unimplemented).
- `senderSetComplete` is a `size>1` heuristic, not a verified "all trusted devices published" gate; a single-peer account or a transient Firestore failure both read as incomplete and keep the unauthenticated legacy path eligible.
- No code-level binding between BiometricPrompt success and `RemoteUnlockSavedCredentialStore.load` (relies on caller discipline; Keystore enforcement is the real backstop).
- No certificate pinning observed for backend hosts (only system trust anchors, `network_security_config.xml:34-36`) — relies on platform CA store + App Check.
- No PII-scrubbing / beforeSend evidence for Sentry — UNKNOWN.

## Crypto/protocol notes
- Vault content: AES-256-GCM, 12-byte SecureRandom nonce, 128-bit tag, AAD = path binding; blob integrity migrated SHA-256 → keyed HMAC (`CloudVaultCrypto.kt:316-326`). Schema-versioned (v1 legacy, v2 current).
- Signal at-rest: per-message random 32-byte content key, AES-256-GCM with canonical-AAD binding; content key HPKE-sealed per recipient (`atRestSeal`), ECDSA-P256 sender signature over length-prefixed domain-separated message; cross-platform NFC byte-parity with Swift.
- Remote Unlock: HPKE DHKEM-X25519-HKDF-SHA256 + ChaCha20-Poly1305, NO_PREFIX variant, structured length-prefixed `info` as AAD (`RemoteUnlockCredentialEnvelopeCrypto.kt:50-95`). E2E to Mac recipient key.
- `sealText` @246 uses `Cipher.DECRYPT_MODE.let { Cipher.ENCRYPT_MODE }` — a confusing but functionally-correct way to pass ENCRYPT_MODE (constant-folds to ENCRYPT). Not a bug, but a readability/audit smell.
