## Threats (T-TRN-NN)
- T-TRN-01 — Cloud-substituted pairing public key → MITM of "verified" iroh link — Spoofing/Tampering (STRIDE); LINDDUN Non-repudiation; Agentic: control-channel hijack — Critical — `FirestoreIrohPairingPublicKeyProvider.swift:27-47`, `HermesIrohRelayTransport.swift:378,385` — Attack path: malicious/compromised cloud backend, Firebase project takeover, or rogue admin writes `users/{uid}/iroh_pairing_keys/host` + a matching signed `iroh_pairing` record pointing at an attacker NodeId; iOS fetches that key (no out-of-band pin, in-memory cache only, never persisted/rotated — `:9-11,28,45`) and "verifies" the attacker's signature, then dials the attacker's QUIC endpoint. — Existing mitigation: docs `firestore.rules:2661-2665` keep these docs server-owned + callable-gated (App Check, high-risk nonce, trusted escrow device); E2E HermesRelayCrypto means the MITM still cannot read payloads (it would have to also defeat the Signal/HermesRelayCrypto trust root). — Gap: no TOFU/safety-code pinning of the host pairing key on iOS; transport identity trust = whatever Firestore returns. — Residual risk: a fully compromised cloud can redirect/hijack the iroh control channel (DoS / selective drop / forced fallback), and could attempt downgrade to read metadata; payload confidentiality survives only because of the separate E2E layer.
- T-TRN-02 — Cloud-controlled inbound allowlist → unauthorized controller admitted or legit controller locked out — Elevation/DoS (STRIDE); Agentic: authz bypass — High — `FirestoreIrohInboundPeerAllowlist.swift:16-29`, gate `HermesIrohRelayHostClient.swift:292` — Attack path: allowlist is read from `iroh_pairing/{conn}/controllers/*` in Firestore; a cloud/admin able to inject a `controllers/{attackerNodeId}` doc adds an attacker NodeId to the Mac's accept set (controller docs are callable-gated `firestore.rules:2774`, but trust still flows through cloud). Conversely deleting docs locks out the user (DoS). — Existing mitigation: callable enforces trusted native escrow + existing host pairing before write; default-deny empty set; per-peer purge on de-allowlist (`:430`); E2E crypto + PhoneControlAuthorityValidator still gate actual control actions downstream. — Gap: no local/out-of-band confirmation of allowlist membership; transport-level admission is cloud-authoritative. — Residual risk: admitted attacker gets a served stream but is still blocked by app-layer authority checks; main impact is reaching the request handler + DoS.
- T-TRN-03 — Attacker-induced downgrade iroh→Firestore — Tampering/DoS (STRIDE); Agentic: forced-path/observability evasion — High — `HermesCompositeRelayTransport.swift:50-74,82-108,119-121` — Attack path: an on-path adversary (or the relay) drops/blackholes iroh dials/streams; for any op except `.chatCompletions` the cascade silently falls back to Firestore long-poll (`:64,108`). Firestore path is cloud-mediated, exposing more timing/size/connection metadata to the backend and removing P2P directness. — Existing mitigation: selected-model chat hard-fails instead of silent reroute (`:119-121,126-132`); each fallback is audited (`:134-148 fallbackToFirestore`); Firestore payloads remain E2E-sealed. — Gap: control-plane + CLI-agent streams fall back automatically; an attacker can cheaply force the more-observable path; no alerting threshold on fallback rate in code. — Residual risk: metadata exposure + degraded P2P guarantees, not payload disclosure.
- T-TRN-04 — Metadata exposure to cloud (NodeIds, relay URL, direct IPs, timing, sizes) — Information disclosure (STRIDE); LINDDUN Linkability/Identifiability — Medium — `FirestoreIrohPairingDirectory.swift:42-81` (reads nodeId/relayURL/directAddresses), pairing record `IrohRelayPairing.swift:14-22`, audit details `HermesIrohRelayTransport.swift:441-447` (localNodeId/targetNodeId/relayURL/directAddressCount), n0 relay sees IP+NodeId+sizes+timing — Attack path: Firestore + n0 relay observe stable NodeIds (long-lived, never auto-rotated), home relay region, the Mac's direct LAN/WAN IPs, byte sizes, and call timing → user localization + presence/usage correlation. — Existing mitigation: payload E2E-sealed; iOS dials without published direct IPs (`HermesIrohRelayTransport.swift:452`); media session telemetry is bucketed/hashed (`firestore.rules:2718-2757`). — Gap: control-plane pairing/audit docs store raw NodeIds + relay URL + direct IPs in plaintext Firestore; NodeIds are persistent identifiers. — Residual risk: metadata-based tracking/correlation by cloud or anyone with read access to the user namespace.
- T-TRN-05 — Stale/replayed pairing record points iOS at a dead/hijacked NodeAddr — Tampering/Spoofing (STRIDE) — Medium — `IrohRelayPairing.swift:133-168 verify` — Attack path: replay an old signed pairing record within the 3-min window (or with skewed clock) to steer iOS to a previously-valid-but-now-reassigned relay/NodeAddr. — Existing mitigation: 180s freshness window (`:74,165`), Ed25519 sig over canonical payload incl. publishedAtMillis (`:95-98`), Mac heartbeat republishes ≤60s (`HermesIrohRelayHostClient.swift:89 pairingPublishInterval=60`). — Gap: no per-record nonce/monotonic counter; freshness relies on client clock; no binding to a session-specific challenge. — Residual risk: bounded 3-min replay window; NodeId reassignment in that window is unlikely but possible.
- T-TRN-06 — DoS via connection floods / unbounded accept loop — DoS (STRIDE) — Medium — `lib.rs:450 accept_one`, `HermesIrohRelayHostClient.swift:289 acceptLoop` — Attack path: any peer that completes the ALPN/QUIC handshake reaches `accept_one`; non-allowlisted peers are rejected only AFTER the handshake + stream accept (`:292`), and there is no per-source rate limit or concurrent-connection cap in the Rust crate. Repeated dials force handshake + Firestore allowlist lookups. — Existing mitigation: default-deny allowlist closes streams fast (`:304`); QUIC idle timeout; consecutive-failure rebuild (`:392-405`). — Gap: no connection-rate limit, no cap on concurrent inbound handshakes, allowlist lookup is per-accept (cached in-memory but reloaded each heartbeat). — Residual risk: CPU/handshake amplification + Firestore read pressure from an unauthenticated flood; no plaintext exposure.
- T-TRN-07 — iroh 1.0.0-rc.0 release-candidate dependency — Tampering/supply-chain (STRIDE) — Low/Info — `crates/openburnbar-iroh/Cargo.toml:20-29` — Attack path: pre-GA transport library may carry unpatched protocol/crypto bugs; pinned to an rc, not a stable line. — Existing mitigation: exact-version pins (`=1.0.0-rc.0`) prevent silent drift; dependabot present. — Gap: shipping production E2E transport on a release candidate. — Residual risk: latent iroh-side QUIC/relay bug not yet found/fixed upstream.

## Gaps / missing controls
- No out-of-band / TOFU pinning of the Mac host pairing public key on iOS; transport identity trust is entirely cloud-mediated (T-TRN-01). No safety-code surface here (contrast the Signal docs).
- No persisted pairing-key cache or explicit rotation/revocation surface for the host key (`FirestoreIrohPairingPublicKeyProvider.swift:9-11` in-memory only).
- No per-source connection rate limit or concurrent-handshake cap in the Rust crate; allowlist rejection happens post-handshake (T-TRN-06).
- Pairing record replay protected only by a 180s client-clock freshness window; no nonce/counter (T-TRN-05).
- Automatic silent downgrade to Firestore for control-plane/CLI streams; no in-code fallback-rate alarm (T-TRN-03).
- Raw persistent NodeIds + relay URL + direct IPs stored plaintext in Firestore pairing/audit docs (T-TRN-04).
- `iroh_fallback_to_wss` is dead/unreachable in the live cascade yet still accepted by `firestore.rules:2707` and present in both Swift/Kotlin audit enums — stale surface, not a vuln.

## Overclaims
- `crates/burnbar-remote/SECURITY.md:29-47` "Invariants" (session-grant binding, host signs nonce, signer store, control-event replay/rate limits) describe the `burnbar-remote-*` prototype which is **NON-SHIPPING and not wired into production** (`SECURITY.md:3-9`); these are NOT controls on the live iroh path. The live transport auth = Swift allowlist + PhoneControlAuthorityValidator, not `ControlPolicyGate`/`InMemorySessionAuthorizer`. Do not credit burnbar-remote authz as an active mitigation.
- `firestore.rules:2680-2682` comment claims the audit `iroh_fallback_to_wss` is "written ... on fallback to the WSS relay" — the WSS relay is retired; this event is no longer produced by the live cascade (which emits `iroh_fallback_to_firestore`). Comment is stale.
- README/SECURITY framing of "verified" pairing can read as cryptographic end-to-end device trust; in code the verification root is a cloud-fetched key with no user-anchored pin (T-TRN-01). "Verified" here means "signature matched a key the cloud handed us," not "out-of-band-authenticated device."

## Crypto/protocol notes
- iroh provides QUIC (TLS 1.3) with NodeId = Ed25519 public key; the QUIC handshake authenticates the remote NodeId. Default relay = n0 public relay set (`lib.rs:286,302 RelayMode::Default / presets::N0`); optional pinned custom relay (`:296`). Relay is a packet mux/NAT-traversal aid, never a TLS terminator → no plaintext at relay.
- Pairing: Ed25519 (Curve25519.Signing) over a canonical pipe-delimited string `openburnbar.iroh.pairing.v1|uid|connectionId|nodeId|relayURL|directAddresses|publishedAtMillis` (`IrohRelayPairing.swift:95-98`). Sound canonicalization (sorted/deduped addrs, version prefix), but trust root is cloud-distributed.
- Payload confidentiality/integrity is a SEPARATE layer (HermesRelayCrypto / Signal) applied by `IrohRelayRequestHandler`; transport tamper/replay/reorder/drop is covered by QUIC (ordered, authenticated, anti-replay within a connection). Cross-connection replay of whole sealed envelopes is an app-layer (AAD/nonce) concern, out of transport scope.
- Frame wire: 4-byte big-endian u32 length prefix + JSON; 512 KiB hard cap both directions (`lib.rs:171-209`).
