- Root-bridge peer auth (HID forward) — `PrivilegedInputExecutionSocketServer.swift:231-246 validateSocketPeer` — moderate — uid 0 bridge bypasses console-user check, gated by code-sig ALONE (intentional; root has no console identity).
- MAIN control-socket peer code-sig gate (RR-3) — `BurnBarDaemonPeerAuthenticator.swift:62-87 validatePeer` + `OpenBurnBarDaemonServer.swift:580-595` — strong — audit-token DR check runs BEFORE any RPC honored; enforced=true in prod.
- Main-socket bearer token — `OpenBurnBarDaemonServer.swift:365-383` + `ConstantTimeCompare.swift` constantTimeTokensEqual — moderate — constant-time; per-RPC `authToken`. Required: `start()` calls `configuration.validate()` which throws `missingSocketAuthToken` (`OpenBurnBarDaemonConfiguration.swift:233-237`), so daemon refuses to launch tokenless.
- Token transport hardening — `OpenBurnBarDaemonManager+Lifecycle.swift:220-232,250-258` — strong — secrets via launchd `EnvironmentVariables`, never argv (not in `ps auxww`); token rotated each reinstall (`:313-322 rotateDaemonSocketAuthToken`, Keychain-backed).

- Mutual auth (client validates SERVER) — `PrivilegedSocketTrust.swift:210-225 validateServerPeer` + `PrivilegedInputXPCClient.swift:242-253` — strong — before writing the macOS-login-password envelope, client checks server UID==expected + first-party code-sig (prevents path-squat credential capture).

## Claims verified against code
- "Only first-party signed apps can connect; daemon validates peer identity" (threat-model:154) — Defensible — main socket: `BurnBarDaemonPeerAuthenticator.validatePeer` `OpenBurnBarDaemonServer.swift:580-595`; HID: `PrivilegedPeerAuthenticator` — note: prod-enforced; dev/unsigned builds disable via env (see overclaim).
- "Main socket holds the same bar as privileged sockets (RR-3)" — Defensible — both go through `OpenBurnBarPrivilegedTrust.validateCodeSignature` with identical DR; `BurnBarDaemonPeerAuthenticator.swift:99-112`.
- "credential envelopes bind request context" (threat-model:154) — Defensible — HPKE `info` includes requestId/sessionId/clientIntentId; recipient compares supplied vs derived info `RemoteUnlockCredentialEnvelopeCrypto.swift:95-106`.
- "hardened runtime / library validation" enforced — Defensible — `PrivilegedSocketTrust.swift:190-198 validateCodeDirectoryFlags` checks both bits.
- "Secrets passed via env, not argv (`ps aux`)" — Defensible — `OpenBurnBarDaemonManager+Lifecycle.swift:220-232`. Note: env vars ARE readable by same-user processes that can read the launchd job / target proc env on macOS-but not via `ps auxww` (kernel hides env for non-owner; same-uid can read).
- "Server authenticated before credential write" — Defensible — `PrivilegedInputXPCClient.swift:242-253`.
- "App Sandbox provides a process sandbox" — NotDefensible — `OpenBurnBar.entitlements:24-26` and `OpenBurnBarRelease.entitlements:16-18` set `com.apple.security.app-sandbox=false`. NO sandbox on the Dev-ID app. Verified.
- "High-risk grants require a single-use local-auth proof bound to the canonical operation hash" — Partial — TRUE at the app/relay layer (`PhoneControlAuthorityValidator`), but the DAEMON does NOT independently re-verify the proof; it trusts the code-signed app peer + its own entitlement/scope/budget gate (`ComputerUseRunCoordinator.swift:10,575-576`). See T-DMN-04.
- "Token auth on main socket" — Defensible (with nuance) — required via `validate()`; but token alone is insufficient and is explicitly demoted to defense-in-depth behind the code-sig gate (`BurnBarDaemonPeerAuthenticator.swift:28-31`).

## Threats
- T-DMN-01 — Compromised first-party app is fully trusted by daemon — STRIDE:Elevation / Agentic:excessive-agency — High — main+HID sockets / `BurnBarDaemonPeerAuthenticator`,`PrivilegedPeerAuthenticator` — attack path: any code running inside (or code-injected into) the signed `com.openburnbar.app`/`com.openburnbar.daemon` passes the DR gate; it then has full main-socket RPC (run dispatch, config writes, provider creds) and can drive HID input. existing mitigation: hardened runtime + library validation block dylib injection of non-first-party code; no sandbox to contain post-compromise. gap: code-sig identity == authZ; no per-operation capability attenuation at the daemon. residual: High — single signed-app RCE = full local agency + credential access. (Acknowledged in threat-model:154 "Signed app compromise ... compromises this boundary".)
- T-DMN-02 — Daemon runs unsandboxed as the login user with broad FS — STRIDE:Elevation — High — daemon process / entitlements — attack path: daemon launched by user LaunchAgent (Application Support path), App Sandbox disabled, reads/writes home dir, holds provider credentials + socket. A daemon-process compromise (e.g. via a parsing bug in an RPC handler) has no OS sandbox boundary. existing mitigation: Gatekeeper/notarization (install-time only), hardened runtime. gap: no runtime sandbox/seatbelt profile; no entitlement minimization on the daemon binary. residual: High.
- T-DMN-03 — Daemon binary path is user-writable; pre-exec sig check is TOCTOU — STRIDE:Tampering/Elevation — Medium — `OpenBurnBarDaemonManager+Lifecycle.swift` / `~/Library/Application Support/.../daemon/OpenBurnBarDaemon` (0755) — attack path: installed daemon binary lives in a user-writable dir and launchd `KeepAlive` re-execs the PATH. A same-uid attacker can swap the binary between the app's `validateStaticCode` check and launchd exec, or directly (launchd does not re-verify signature). existing mitigation: RR-3 LIVE peer code-sig gate on every socket — a swapped daemon binary fails the DR when the app connects, so it cannot serve RPC to the real app (load-bearing). Pre-exec check `:216` + atomic swap reduce window. gap: launchd itself will still EXEC an unsigned/swapped binary as the user (it just can't impersonate the daemon to the app); a malicious swapped binary could still abuse whatever the daemon's own creds/entitlements grant before any app connects. residual: Medium — peer-auth contains impersonation; does not contain a hostile binary's own actions.
- T-DMN-04 — Daemon does not cryptographically re-verify the phone local-auth proof — Agentic:authority-confusion / STRIDE:Elevation — Medium — `ComputerUseRunCoordinator` vs `PhoneControlAuthorityValidator` (app) — attack path: the single-use Ed25519 op-hash-bound proof is validated only in the app/relay; the daemon's run gate is entitlement+scope+burst-signature (`ComputerUseRunCoordinator.swift:65-66,575-576`), trusting the app to have enforced step-up. If T-DMN-01 holds (app compromised) the proof requirement is bypassed for shell/system-input. existing mitigation: app peer code-sig gate; daemon scope/deny/budget gate. gap: no daemon-side proof verification == proof binding is only as strong as app integrity. residual: Medium (High if app is compromised).
- T-DMN-05 — Peer code-sig enforcement disabled by env var — STRIDE:Spoofing — Medium — `OpenBurnBarDaemonMain.swift:76-84 makePeerAuthenticator` — attack path: a same-uid process that can influence the daemon's launch environment sets `OPENBURNBAR_DAEMON_DISABLE_PEER_CODESIG=1`, dropping the main-socket gate to `.disabled` (every peer admitted); only the bearer token remains. existing mitigation: launchd plist is app-written 0600 (`Lifecycle.swift:290-293`); bearer token still required. gap: env-flag opt-out exists in prod binary; if attacker controls plist/env they remove the load-bearing gate. residual: Medium.
- T-DMN-06 — HID root-bridge peer trusted by code-sig only (no UID anchor) — STRIDE:Spoofing — Low — `PrivilegedInputExecutionSocketServer.swift:231-246` — attack path: a root process forging the first-party identity could drive locked-screen input; requires root + first-party code-sig (Apple anchor + Team ID), which a non-first-party root process cannot satisfy. existing mitigation: full DR + CD-flag check on the root peer. gap: relies entirely on code-sig (acceptable; root already wins most games). residual: Low.
- T-DMN-07 — `auditToken` read via private KVC on NSXPCConnection — STRIDE:Spoofing — Low — `PrivilegedInputXPCPeerValidator.swift:25-36` — attack path: uses private `auditToken` selector (Dev-ID only, not MAS); if Apple removes it the validator returns nil -> `auditTokenUnavailable` (fail-closed). existing mitigation: fail-closed on nil. gap: SPI fragility, but socket path (LOCAL_PEERTOKEN) is the primary, robust path. residual: Low.
- T-DMN-08 — HPKE info field is HPKE `info`, AEAD AAD is empty (cross-platform) — STRIDE:Tampering — Low — `RemoteUnlockCredentialEnvelopeCrypto.swift:5-11,68-72` — attack path: AEAD associated data fixed empty for Tink interop; context binding relies on HPKE `info` (key-schedule binding) + the Ed25519 authority hash over ciphertext+info. existing mitigation: info mismatch rejected pre-decrypt (`:103-106`); authority signature covers both fields. gap: none material — info is cryptographically bound into the HPKE context. residual: Low (documented design, verified sound).

## Gaps / missing controls
- No OS process sandbox on the daemon or the main app (App Sandbox=false on both Dev-ID lanes). Compromise containment relies only on hardened runtime + Gatekeeper.
- Daemon does NOT re-verify the single-use local-auth proof; proof binding is enforced app-side only — the daemon trusts the signed app to have done step-up (T-DMN-04).
- Daemon binary lives in a user-writable path; launchd does not verify signature at exec — only the live socket peer-auth contains impersonation, not a hostile binary's own actions (T-DMN-03).
- Production env escape hatch `OPENBURNBAR_DAEMON_DISABLE_PEER_CODESIG=1` ships in the released binary (T-DMN-05).
- Code-sign identity is used as authorization (no per-RPC capability attenuation on the main control socket) — a compromised first-party app/daemon = full local agency (T-DMN-01).

## Overclaims
- "App Sandbox ... provides a security boundary" — the entitlement comment frames Gatekeeper/notarization as an "alternative security boundary" (`OpenBurnBar.entitlements:18-21`), but there is NO runtime sandbox; this is an install-time check only, not a post-compromise containment boundary. Record as overclaim if any doc implies the daemon/app is "sandboxed".
- Any doc claim that high-risk grants are "bound to a single-use local-auth proof" should be qualified: the binding is enforced in the app/relay (`PhoneControlAuthorityValidator`), not re-checked by the privileged daemon, so it does not survive app compromise (T-DMN-04).
- "Secrets not visible to local users" — env vars are hidden from `ps auxww` and from OTHER uids, but a SAME-uid process can read the daemon's environment; phrasing should say "not in argv / not cross-user", not "invisible to local users".

## Crypto / protocol notes
- HPKE: Curve25519 + HKDF-SHA256 + ChaCha20-Poly1305 (`RemoteUnlockCredentialEnvelopeCrypto.swift:70`). Encapsulated key (32B) prepended to AEAD ciphertext (`:74-76,108-115`). Context binding via HPKE `info` (length-prefixed canonical field encoding `:124-151`), re-derived and compared by recipient before `open` (`:95-106`) — sound. AEAD AAD intentionally empty for Android Tink interop; acceptable because `info` is bound into the key schedule.
- Designated Requirement: `anchor apple generic and certificate leaf[subject.OU] = "4Y367DF25B" and (identifier "com.openburnbar.app" or .daemon or .privileged-input-execution or .virtual-hid-bridge)` (`PrivilegedSocketTrust.swift:69-71`). Exact-identifier OR list (M-9 fix: no prefix operator in CSRL). Hardened-runtime + library-validation enforced programmatically (`:190-198`), not in DR string — correct.
- LOCAL_PEERTOKEN pinned to 0x006 with a live-socket regression test referenced (`PrivilegedSocketTrust.swift:78-101`) — prior 0x102 typo silently fail-closed; now guarded.
- Local-auth proof signable payload: proofId|deviceId|signedIntentHash|authenticatedAt|expiresAt, Ed25519 over phone verifying key (`PhoneControlAuthorityValidator.swift:530-537`). signedIntentHash == canonical grant-request hash (op-hash binding). Single-use + persisted + TTL-bounded.
