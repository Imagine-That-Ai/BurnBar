## Threats (T-CVS-NN)
- T-CVS-01 — Server strips `signalEnvelope` to force unauthenticated legacy decode — Tampering/Repudiation (STRIDE) / agentic-supply-chain — Critical→**Medium (latent; only bites once Signal is activated)** — AssistantChatHistoryStore.kt:817 reader fallback — path: dual-write leaves legacy `sealedPayload`; malicious Firestore writer deletes the `signalEnvelope` field; reader sees `data["signalEnvelope"]==null` → FallThrough → decodes unauthenticated legacy; sender-auth fail-closed policy never runs because no envelope is present — existing mitigation: legacy AES-GCM still confidential + path-AAD (forgery still blocked), fail-closed only for PRESENT-but-broken envelopes — gap: no per-doc "must be Signal" pin; strip is indistinguishable from legacy-only doc — residual: full sender-auth bypass survives until the legacy floor is removed post-activation.
- T-CVS-02 — `senderNotTrusted` legacy downgrade window during rollout — Spoofing — Medium — SignalAtRestFallbackPolicy.swift:42-45; senderSetComplete derived `trustedSenderPublicKeys.size > 1` (AssistantChatHistoryStore.kt:818) — path: before every trusted device publishes its identity, `senderSetComplete==false`, so an unknown-sender envelope is treated as legacy-eligible; a server-forged envelope naming an UNPUBLISHED device id is accepted as a readiness gap rather than dropped — mitigation: only `senderNotTrusted` is downgrade-eligible; signature still required once the id resolves — gap: heuristic `size > 1` can be wrong with exactly one legitimate cross-device peer — residual: time-boxed spoof window during activation ramp.
- T-CVS-03 — Identity private key extractable on compromised/unlocked endpoint — Information Disclosure — High — SignalIdentityKeyStore.swift:88-94 / AndroidLocalSecretBox.kt:1206-1221 / CloudVaultCrypto.swift:1416 — path: keys at `WhenUnlockedThisDeviceOnly` (no biometric/`SecAccessControl`) and AndroidKeyStore wrap without `setUserAuthenticationRequired`/StrongBox; any code running as the app while device unlocked reads raw private/vault key bytes → can forge sender-auth + decrypt all at-rest — mitigation: device-only accessibility blocks iCloud/backup exfil; TEE wrap blocks raw-prefs theft — gap: no hardware-bound non-extractable signing, no per-use auth — residual: endpoint compromise = total at-rest + sender-auth compromise (no forward secrecy to limit blast radius).
- T-CVS-04 — Weak/empty passphrase + low-iteration recovery bundle brute-forced offline — Information Disclosure — Medium — DatabaseEncryptionService.swift:161-166 (no password-strength check), :223-225 (iteration count read from attacker-controlled bundle on import) — path: `exportRecoveryBundle("")` derives a key from an empty/weak password at 100k iters (< OWASP 600k); bundle on disk/cloud is offline-grindable; on import the iteration count is trusted from bytes 17..21 with no floor — mitigation: random 16-byte salt + AES-GCM integrity — gap: no min-length/zxcvbn gate, no import-side iteration floor, iteration count below current guidance — residual: a leaked bundle with a weak passphrase yields the SQLCipher DB key.
- T-CVS-05 — Forward-secrecy absent for at-rest sealing — Cryptography/Repudiation — Medium — SignalAtRestSealer.swift:67-85 (recipient long-lived identity key seals every content key) + CloudVaultCrypto.swift:1398-1430 (persistent vault key) — path: content keys wrap to a static recipient identity key and the vault key is long-lived; a future identity/vault-key compromise retroactively decrypts all historically-sealed docs an attacker captured — mitigation: per-message random content key limits cross-doc reuse; key rotation exists (`rewrapCloudVaultDocument` CloudVaultCrypto.swift:677) but rewraps, not ratchets — gap: no ephemeral/ratcheted at-rest scheme — residual: no PFS (threat-model line 33 concedes this for the relay leg; same applies at rest).
- T-CVS-06 — Legacy v1 AAD acceptance on open keeps a weaker domain-separation path live — Tampering — Low — CloudVaultCrypto.swift:1094-1102 `aadData(matching:)` + :605-606 schema-v1 opens with NO AAD — path: an attacker who can present a v1-schema envelope opens under the no-AAD branch, sidestepping path binding — mitigation: still requires the correct vault key (confidentiality intact); v1 is migration legacy — gap: no enforced cutover removing v1 acceptance — residual: weakened relocation binding for legacy docs only.

## Gaps / missing controls
- No per-document "Signal-required" marker, so a stripped `signalEnvelope` silently downgrades to legacy with no sender-auth (T-CVS-01). The dual-write legacy floor is the structural blocker to a hard fail-closed.
- iOS keys lack `kSecAttrAccessControl`/Secure Enclave; Android wrap key lacks `setIsStrongBoxBacked` and `setUserAuthenticationRequired` (CloudVaultCrypto.kt:1210-1218) — no hardware-bound, non-extractable, per-use-auth signing.
- Recovery bundle: no passphrase-strength gate, no import-side PBKDF2 iteration floor, iteration count below OWASP-2023 (T-CVS-04).
- No key revocation/compromise response wired at the at-rest layer beyond document rewrap; compromised identity key has no CRL/blocklist at open time other than removal from `trustedSenderPublicKeys`.
- No forward secrecy / ratchet for at-rest content (T-CVS-05).

## Overclaims
- Comment "The PRIVATE key never leaves the device" (AndroidSignalIdentityKeyStore.kt:16) overstates protection — it is true only against network exfil; the raw bytes are reconstituted in app memory and the on-disk wrap is software/TEE, not StrongBox/user-auth-bound.
- Doc-level "Secure Enclave/StrongBox where available" expectation (threat-model line 167) is NOT realized in code for vault/identity/DB keys — all use plain Keychain generic-password / AndroidKeyStore software-or-TEE wrap. Conceded in the same line but worth pinning.
- Any prose implying CloudVault at-rest is "E2EE" should be read as honest-but-curious-server confidentiality, NOT forward-secret and NOT sender-authenticated in production (Signal sender-auth is inert until activation).

## Crypto/protocol notes
- AEAD: AES-256-GCM everywhere (CryptoKit / `AES/GCM/NoPadding`), 12-byte random nonce, 128-bit tag, random keys from `SecRandomCopyBytes`/`SecureRandom`. No nonce-reuse risk observed (fresh nonce per seal).
- Recipient seal: libsignal `PublicKey.seal`/`PrivateKey.open` (Curve25519 sealed-sender / HPKE-style) with `info` + `associatedData` both derived from canonical binding — strong domain separation; relocation-bound.
- Sender-auth: libsignal Curve25519 XEd25519 signature over a length-prefixed, NFC-normalized, byte-canonical message (domain + info + ciphertext + sorted wraps). Verified against PINNED key — server cannot forge. Byte-parity with Kotlin asserted by shared fixtures.
- Vault-key wrapping: P256 ECDH + HKDF-SHA256 (`OpenBurnBar-Escrow-v1`, empty salt) → AES-GCM (CloudVaultCrypto.swift:966-1004). Recovery-key wrap: HKDF-SHA256 with FIXED salt `recoverySalt` (CloudVaultCrypto.swift:403/1009-1014) — acceptable given high-entropy 35-byte base32 recovery code.
- HMAC/HKDF search subkeys use empty salt + distinct info strings (CloudVaultCrypto.swift:1075-1160) — deterministic by design (dedup/search trapdoors); not a confidentiality boundary for the vault key.
