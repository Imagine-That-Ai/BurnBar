## 1. Executive Summary

**The biggest truth about this codebase: it already knows almost all of its debt — it just cannot hold a finding closed.** Thirteen overlapping review documents, two diligence reports, a remediation taxonomy, and four debt-ratchet budget tools exist; yet `Task.sleep` test flakiness has been flagged in three successive QA reviews and never fixed, the quarantined-test revival dates lapsed a month ago unreviewed, the `try?` ratchet target (≤120) is missed 6.7× with the baseline being *bumped up* (`chore(debt): bump try? baseline 797→800`), and the freshest, densest registers are untracked files visible only on one machine. The repo's problem is not awareness; it is **closure**.

Three structural facts dominate everything else:

1. **Line-level quality is genuinely high; control-level quality is theater.** Lane after lane verified above-norm discipline (zero `try!`/`as!` in 639 Mac files, one `any` in all of functions/src, strict TS everywhere, hostile crypto KATs on three platforms). But nearly every gate that measures *quality* rather than *compilation* is currently unable to fail: the diff-coverage gate auto-passes the daemon, all of mobile, and all view code via presence checks (carved out 6 minutes after a 3.2%-vs-80% red run — receipts in the 06-11 diligence); detekt runs in **no** CI workflow; ktlint "passes" against a frozen 14,581-entry baseline while CI prints "no violations found"; both Jacoco gates are dead tasks; the functions lint gate silently skips every top-level `src/*.ts` file via an unquoted glob; the Signal honesty-copy gate is wired into zero workflows while another gate's comments claim it's enforced; the counsel-approval release gate verifies hex *shape*, never a signature; the nightly E2E is 10/10 lifetime-red with DAST that cannot fail; and ~117 passing tests across services/, tools/, and quota-runner run in **zero** CI lanes.

2. **Production is operationally dark and, until this week, unrecoverable.** Live-verified on 2026-06-11: production Firestore had **no PITR, no backups, no delete protection** — practical corruption-recovery capability of *zero* — while the incident runbook prescribes "restore from backup" and an accepted ADR cites a backup mechanism (B-BE-1) that was never built, and daily fleet-wide destructive automation (privacyBackfill sweeps, recursiveDelete, panic drains) runs against that store. All 16 GCP alert policies notify an **unregistered domain** (NXDOMAIN). Sentry is dead on functions (DSN never provisioned), never started on iOS, and effectively off on Android. The production deploy lane is wedged (submodule checkout bug), `rollback.sh` would deploy a year-old beta with all runtime config dropped, three Cloud Run services deploy only from a laptop, and Android 13+ users can never see a notification because `POST_NOTIFICATIONS` is never requested. Two paid-surface product breaks are live right now: burnbar.ai ships a **fake Firebase API key** (sign-in dead on /link and /hermes/connect), and the hosted-MCP path advertises OAuth endpoints that don't exist while every consumer discards the refresh token — the paid CLI hard-401s 15 minutes after login, forever.

3. **Growth happened by cloning, and nothing ever forces consolidation.** 45+ files exceed 1,500 lines and they are exactly the highest-churn files (HermesService.swift: 58 commits, 4,907 lines; HermesTabView, FunctionsRepository, firestore.rules — the churn×size hotspot list and the god-file list are the same list). The flagship "TypeSpec schema canon" is a façade: the 15 `.tsp` files are never compiled, 9 of 14 generated type files are dead, and the real schema registry is a 3,261-line `legacy.ts` plus 4th and 5th hand-written Swift/Kotlin copies held together by 54 prose "mirrors the iOS" comments. Entitlements — the paywall — are implemented 4–9 independent ways. CloudVault crypto constants exist in 8 hand-synced copies across 5 languages. Mac↔iOS share a SwiftPM package built for sharing, yet 55 identically-named Swift twin files have already drifted behaviorally.

**Root cause in one sentence:** a solo founder driving an AI-agent fleet produced ~1.0M LOC in ten weeks (86% of 1,385 commits by one person, 0 of 211 PRs ever human-reviewed, 25.7% of all commits fixing prior work), and production throughput permanently outran governance capacity — so controls were added in response to audits but became negotiable the moment they went red.

**The good news, equally evidence-based:** the dangerous debt is overwhelmingly *cheap*. Of 58 fix-now findings, 56 are S/M effort. The single worst operational exposure (Firestore backup) is a one-day fix, two of it being console commands. The gate-honesty failures are mostly one-line wiring fixes to machinery that already exists and already works. The team demonstrably knows how to pay debt down when it's framed as a project (CloudSyncService 2,102→230-line facade; the fatalError-on-init crash replaced with real startup recovery; the P0-7 rollup rebuild is genuinely good engineering). The plan below is sequenced so that the first two weeks buy back data safety, detection, and gate honesty — after which every later refactor lands on ground that can be trusted.

## 2. Top Debt Themes

**T1 — Self-certifying controls (gate-integrity collapse).** *Systemic; the meta-theme.* Every quality gate that became inconvenient was allowed to self-certify: presence-based coverage carve-outs, detekt/ktlint/Jacoco disconnected, unquoted lint globs, honesty gate unwired, signature gate checking shape not signatures, silent-skip paths in required checks, `continue-on-error` QA, ~117 tests in zero CI lanes, ratchet baselines raised in-place when they block. The 06-11 diligence proved this class with receipts; this audit found it is broader than the diligence knew. *Everything else in this plan depends on fixing T1 first — refactoring under dishonest gates just churns risk.*

**T2 — Dark and (until now) unrecoverable production.** No Firestore backup/PITR/delete-protection (live-verified); NXDOMAIN alert channel; issue-dedupe that mutes new failures behind standing reds across all four alerting workflows; Sentry dead on functions, iOS, and effectively Android; wedged production deploy; rollback that would ship a year-old beta with empty config; laptop-only deploys for 3 Cloud Run services; no mobile store automation; Android notifications dead on API 33+; mobile crash-blind on both platforms. Detection-without-delivery is zero detection.

**T3 — The contract canon is a façade; every contract is N hand-synced copies.** TypeSpec never compiled (1 of 14 domains drift-checked, via substring match); `legacy.ts` as the real 3,261-line schema registry; quota snapshots in 4 representations with fail-open decoders on the product's core sync wire; the relay frame protocol's 1,348-line Kotlin mirror hand-maintained outside all drift control; entitlements implemented 4–9 ways; CloudVault crypto in 8 copies / 5 languages; 454 `[String: Any]` at the iOS↔Firebase boundary; a 77-cast untyped translation matrix duplicated across two daemon executors. The crypto byte-contracts (HPKE v3, signal AAD, control-seal, media AEAD) prove the team's fixture-based parity method works — it just was never extended past crypto.

**T4 — God files at exactly the churn hotspots, with missing structural tiers.** 45+ files >1,500 lines; the top-25-by-commit-count list and the god-file list coincide (HermesService 58 commits/4,907 lines; firestore.rules 73 commits/4,179 lines; HermesTabView 41/4,537). Missing tiers, not just big files: no controller/interactor layer on iOS (24-closure prop-drilling chains ×3 surfaces), no composition root on iOS (62 singletons) or Android (four competing object-lifetime regimes; HermesService constructed per-screen and never destroyed), a second mission-execution engine living inside a GUI-app Firestore listener, and OpenBurnBarCore as a 79k-LOC kitchen sink (24% SwiftUI) linked wholesale by the privileged daemon.

**T5 — Same-language duplication (cheaper to fix than the cross-language tax, and untracked).** The ~2,900-line Popover/Dashboard QuickSwitch fork (every change already applied twice by hand, proven by shared commits); 55 identically-named Mac/iOS Swift files with proven behavioral drift (budget enforcement hardcoding one model's pricing on iOS); four hand-rolled privileged Unix-socket server scaffolds with drift already visible in EAGAIN handling and magic constants; three keychain CRUD implementations in the daemon; Mac/iOS CloudVault sealing near-twins drifting on the exact at-rest sender-auth surface the master remediation calls its top open P1.

**T6 — The privileged-input lane regressed while being "hardened" (in-flight on this branch).** The dirty tree replaces a launchd Mach service with a squattable `/tmp` socket with zero client-side server authentication on the path that types the macOS login password; the committed M-9 fix shipped a wrong `LOCAL_PEERTOKEN` constant (0x102) proving the gate was never exercised live; peer-auth tests are theater-grade while 409 untested lines land under a coverage carve-out; the helper runs unsupervised (LaunchAgent deliberately removed); and the panic kill-switch's app-side activation silently fails against a root-owned `/var/run` path. This is the most dangerous surface in the product carrying the weakest reliability and test story in the repo.

**T7 — Data lifecycle was never built (local and cloud).** Locally: `INSERT OR REPLACE` bypasses FTS delete triggers — 1.94M orphaned full-text copies, 11.5 GB of a 14.3 GB live DB holding ~41 MB of logical text; retention purge is a no-op stub; projection_jobs is 99.9% dead rows; the daemon journal appends forever (126 MB); the refresh pipeline does O(entire-history) work every 60 seconds. In the cloud: zero TTL policies while six-plus collections write `expireAt` fields expecting one (pop_nonces grows one doc per authenticated gateway request); a 36-composite cartesian index matrix over-indexes an unused facet while the two advertised facets have no index and fail at runtime; chat history persisted as one monolithic JSON rewritten synchronously per turn on the main actor.

**T8 — Enforcement theater in concurrency and dependencies.** Strict-concurrency "complete" is warnings-only on Xcode targets (Swift 5.10 mode) and entirely absent from the SwiftPM-built crypto and daemon packages; `@unchecked Sendable` grew 26→173 in a month with 9 audited; nine CloudSync services share a copy-pasted check-then-act race behind those annotations. Dependency side: 0 of 80 Dependabot PRs ever merged (40 open incl. security bumps), renovate.json is dead config, vulnerability scanning covers 2 of 16 npm lockfiles / 0 Python surfaces, the most security-sensitive host-side component is vendored as 113 `.pyc` files with no source or dependency manifest, and qa.yml runs `curl | sh` with ~15 production secrets in scope.

**Process meta-theme — reviews supersede instead of closing.** New dated reports re-litigate old ones (QA ×3, architecture ×2, diligence ×2); ad-hoc ID schemes (LB-x, NB-x, P0-x, C-x…) never cross-reference; the SOTA plan was moved to a gitignored `internal/` that doesn't exist in this tree, leaving dangling references from an accepted ADR. The only machine-tracked debt (error/type budgets, quarantine manifest) is the only debt with any closure behavior — and even those ratchets are being raised, not lowered.

## 7. Root Cause Analysis

1. **Throughput permanently outran governance.** ~1.0M tracked LOC and 1,385 commits in ten weeks of repo life; one author = 86% of commits; 206 merges with zero human reviews under branch protection *requiring* one (enforce_admins toggling is routine operating procedure); commit velocity swings 20→339/week with the spikes being audit-remediation sprints — maximum change volume landing under deadline with minimum review. A quarter of all commits (`fix:` 25.7%) repair prior work.
2. **Gates became negotiable when red.** The documented sequence — red coverage run → carve-out commit 6 minutes later → green → solo-merge in 54 minutes — plus `chore(debt): bump try? baseline 797→800`, CI-timeout "round 2" raises (×4 since May), and a smoke test silenced 25 minutes after its first true positive. The pattern: under pressure, the gate is adjusted to pass the work rather than the work adjusted to pass the gate. No rule distinguishes "fixing a broken gate" from "blinding a working one."
3. **Mechanisms get built; migrations get skipped.** TypeSpec emitters exist, never compiled; parser_checkpoints table built (v29 migration + store wired), zero parser callers; generated Swift/Kotlin types emitted, unconsumed; Jacoco verification tasks defined, never invoked; detekt config tuned, wired nowhere; the red-team suite written, env-gated off; the honesty gate hardened, never executed; renovate.json authored, dead. Building the mechanism reads as progress and demos well; wiring + migrating is the boring half that never gets scheduled. *This is the single most repeated pattern in the repo.*
4. **Growth by cloning, with no consolidation pass.** Android is an explicit screen-by-screen port of iOS; iOS twin-files clone Mac logic; gateway endpoints are paste-adapted; the security remediation hand-copied a fourth socket-server scaffold into the TCB *while remediating*. Cloning is the fastest primitive available to AI-driven development, and nothing in the workflow (no reviewer, no duplication ratchet at the file level) ever forces the merge-back.
5. **Reviews are events, not ledgers.** Each new review re-litigates the last (QA ×3, architecture ×2, diligence ×2) under fresh ad-hoc IDs; closure status requires reading the newest doc; April findings (gateway TLS, daemon switch) have no later disposition at all; the densest plans live in untracked files or a gitignored `internal/` directory referenced by an accepted ADR. Findings have no owner, no expiry, no state machine — so they go stale instead of closed.
6. **Feature surfaces ship without their delivery system.** Mobile, services/, tools/, quota-runner — all feature-complete, all missing some or all of CI, deploy automation, telemetry, and rollback. The main lanes (Mac app, functions) got progressively hardened delivery; everything added later inherited none of it by default.

## 8. Debt Reduction Strategy

**Philosophy: restore the integrity of the control plane first; then collapse copies onto single sources of truth; then decompose structure. Never refactor on ground you can't trust.**

Prioritization framework (applied to produce the phases):

| Rank | Criterion | Rationale |
|---|---|---|
| 1 | Irreversibility (data loss, security exposure, public trust) | Can't be fixed after the fact: C1, C9, C10 |
| 2 | Detection (can we even see failures?) | Multiplies every other risk while absent: C3, H13, C11 |
| 3 | Gate honesty (does green mean anything?) | Precondition for safe refactoring at AI velocity: C6, H1–H10 |
| 4 | Leverage (one fix kills a recurring tax) | Contracts, dedup, CI build caching: H24, H27–H30 |
| 5 | Structure (rewrite prevention) | God files, composition roots, Core split |
| 6 | Polish (long tail) | Naming scar tissue, doc drift, dead code |

**Explicit tradeoffs:**
- God-file decomposition — the most *visible* debt — is deliberately deferred to Phase 3, behind gate honesty and contracts. Refactoring 4,900-line files while the coverage gate auto-passes them and the contracts they serialize have no drift protection is how you ship regressions at scale.
- TTL/scaling ceilings (zero TTLs aside, which is cheap and compounding) are scheduled, not immediate: they hurt at 10×, not today, and detection must exist first so we *see* them start to hurt.
- The cross-language (Swift/Kotlin/TS) re-implementation tax is treated as **architecture to manage, not debt to eliminate**: native apps were a deliberate choice. What gets fixed is the *unprotected* drift (fixtures + drift gates), not the existence of three implementations.
- Accepted intentionally (record, don't fix): English-only v1 (write the ADR + add the string-catalog seam *during* god-file decomposition, costing near-zero); single firestore.rules file (Firestore constraint — fix the internal duplication via generation instead); quota-runner's screen-scraping approach (no provider API exists — harden with golden transcripts instead); serial scheduled workers until ~1k connected accounts.

## 12. Guardrails (how to do all of this safely)

1. **Behavior-pinning before movement.** Every decomposition PR is preceded by (or includes) characterization tests pinning current behavior at the seam being cut; mechanical-move PRs contain *zero* logic changes (enforced by review prompt + `git diff --stat` shape).
2. **Gate changes ride alone.** Any edit to scripts/ci/, scripts/diff-coverage*, workflow gates, or budget baselines ships in a dedicated PR containing a paired *negative test* (a thing that must fail) and never lands in the same PR as the code it gates. This single rule prevents the carve-out failure mode with receipts.
3. **Ratchet-bump governance.** Raising any baseline (try?, unsafe-cast, @unchecked, ktlint, coverage waiver) requires a linked issue, an expiry date in the waiver file, and shows up in the weekly metrics diff. Policy-as-code: the budget checker rejects baseline increases unless the commit message carries `debt-bump: <issue-url>`.
4. **Concurrent-editor collision control.** Each work package (§15) declares its exclusive file set; the orchestrator never schedules overlapping sets simultaneously (this repo has a recorded history of concurrent-editor file corruption — re-verify every edit on shared files like project.yml).
5. **Privileged-path double review.** Anything under OpenBurnBarDaemon/, ComputerUseCore, or SignalCore gets an independent adversarial-review agent pass before merge (bus factor 1 means the "second human" must be synthesized).
6. **Flags & parallel-run for behavior-bearing migrations:** chat-history store migration runs dual-write/read-old → read-new behind a local flag for one release; rules generation lands as byte-identical output first (diff == empty proves the generator), then refactors; sealing-path consolidation goes platform-by-platform behind the existing RC kill switches with parity vectors green first.
7. **Restore/rollback drills precede destructive work.** No mass-deletion or migration PR (FTS repair, TTL backfills, retention) before the Phase-0 restore drill evidence exists.
8. **Docs in the same PR.** Every workstream updates the runbook/ADR it touches (the audit found three runbooks prescribing procedures that don't exist — that class is now a review check).
9. **Definition of closed.** A finding is closed only when: fix merged + gate/test preventing recurrence exists + register row updated with the commit hash. "Fixed but ungated" stays open at reduced severity.

## Appendix B — Lane Health Verdicts (31 lanes)

## q-mac (Code Quality & Maintainability)
The AgentLens lane is disciplined at the small scale and eroding at the large scale: zero `try!`/`as!` in 639 production files, only 4 TODO/FIXME markers, centralized typed Notification.Name constants, and visible debt repayment since the April review (ChatPanel decomposed into Components/, DashboardView stubs implemented, an auto-generated TECH_DEBT_METRICS.md gate). The dominant failure mode is unconsolidated AI-velocity growth: six view files over 2,000 lines, a wholesale popover/dashboard QuickSwitch fork (~2,900 lines plus duplicated UI test suites), four cloned detail-sheet scaffolds inside the 4,383-line ProjectsView, and a 9-function auth-helper layer copy-pasted across three settings surfaces. The sharpest correctness risk is the stringly-typed chat-backend plumbing — four divergent runtime-alias tables, one of which already silently drops 4 of 9 backends — combined with ChatSessionController's hand-rolled per-backend property sets, making every backend addition shotgun surgery. There is also one frozen refactor (dead DashboardSidebar kept alive by its own test suite) that quietly corrupts the coverage signal the launch-diligence process depends on. Existing debt registers track the services-side themes well but miss almost all of the view-layer duplication found here; UsageAggregatorParsers shows that even tracked items are losing ground to feature accretion. OpenBurnBarWidget/ and OpenBurnBarKeyboard/ are small, clean, and not a concern.

## q-core (Code Quality & Maintainability)
OpenBurnBarCore/Sources is, line-by-line, disciplined code — typed errors in crypto paths, only 2 truly-empty catch blocks in 97.8k LOC, real cross-language wire-vector tests, and a genuinely good schema-sync/ADR governance apparatus around it. The debt is structural, not local: the base OpenBurnBarCore target is a 79k-LOC kitchen sink (24% SwiftUI views, plus E2EE crypto, AppKit process launchers, vector indexes, and a 3.3k-line brand animation) that the privileged daemon links wholesale; the package's public API has accreted ~1,400 public types of which ~400 are never named outside the package; and the two highest-traffic shared contracts (quota snapshots and the realtime relay frame protocol) have escaped the otherwise-strong drift-control machinery, leaving three-to-four hand-synced representations bridged by fail-open decoders. The headline risks for the next year are silent schema drift on the Mac→iOS quota sync wire and the relay protocol's hand-maintained 1,348-line Kotlin mirror falling behind a 2,591-line Swift god-file that is still growing (Phase 14 frames added recently). Most of the big-ticket items are already named in DILIGENCE_REPORT_2026-06-10.md and ADR 003/004 — the gap is execution, not awareness.

## q-daemon (Code Quality & Maintainability)
OpenBurnBarDaemon/Sources is a tale of two codebases. The typed RPC plane (BurnBarRPCMethod enums, versioned envelopes, namespaced handler extensions), the router scorecard, and the peer-authentication core are disciplined and well-tested. The debt is concentrated in two places: (1) the gateway proxy path, where BurnBarHTTPGatewayServer.swift has grown 6x (586→3,562 lines) since ARCHITECTURE_REVIEW flagged it, with three copy-adapted endpoint handlers feeding 31 call sites of a 19-parameter logging function, on top of a ~77-cast untyped [String: Any] wire-translation matrix split across two executor files; and (2) the privileged executables, where the in-flight security remediation just hand-copied a fourth POSIX socket-server scaffold (visible drift in EAGAIN handling, magic 0x006 literals, and console-user resolution) into the highest-trust code in the product, with zero direct tests and a coverage gate that was carved out for exactly these files. Secret handling adds a silent-failure layer: three keychain CRUD implementations with divergent semantics, a plaintext continuity-vault fallback, an OAuth refresh that swallows all errors, and not a single log line in the 2,612-line executor file. None of this is currently broken — the 5,047-line gateway test file is real protection — but the duplication tax means the next provider-format or privileged-protocol change must be made correctly in 3-4 places, and the silent secret fallback chain will turn the first OAuth-revocation incident into an undiagnosable support fire.

## q-ios (Code Quality & Maintainability)
OpenBurnBarMobile is a healthy-at-the-line-level, sick-at-the-file-level lane: 401 Swift files / ~138k LOC with disciplined doc comments, zero TODO/FIXME markers, consistent modern async/await (only 3 completion-handler APIs, all OS-framework delegates — the "inconsistent async" hypothesis did NOT reproduce), and real unit tests (HermesServiceTests alone is 3,254 lines). The debt concentrates in five god files (HermesService 4,907; HermesTabView 4,537; ScreenShareViewerView 4,512; HermesSettingsView 3,654; FunctionsRepository 3,112) that each fuse models, transports, stores, and UI into single compilation units — already flagged as P2-1 in DILIGENCE_REPORT_2026-06-10.md but untouched by the current remediation branch, whose dirty-tree changes in this lane are visual polish plus streaming-throttle hardening. The two highest-leverage debts NOT well tracked elsewhere are (1) same-language Mac↔iOS duplication — 55 identically-named Swift files, several near-verbatim logic copies with proven semantic drift, despite OpenBurnBarCore already being linked by both targets — and (2) a pervasively untyped Firebase boundary (454 `[String: Any]` occurrences, 70 JSONSerialization call sites, hand-rolled parsers copy-pasted 4-5x within one file). Dead code is minimal (one superseded 244-line model-picker sheet found); the real risk is regression-by-drift between duplicated Swift twins and between the iPhone/iPad Square shells.

## q-android (Code Quality & Maintainability)
The Android lane is feature-rich and not sloppy at the micro level — the 2026-05-31 detekt campaign (de4b8f92f) was a genuine 730-file remediation with documented suppressions, the new seal lanes carry cross-platform conformance-vector tests, and the *Sections decomposition, while badly named, mostly produced semantic units. The structural problem is that every quality control is now disconnected: detekt runs in no CI workflow, ktlint 'passes' against a frozen 14,581-entry baseline while CI prints 'no violations found', and the Kotlin diff-coverage gate was removed from the PR harness yesterday (941faf698) — so ten days of heavy churn, including the in-flight security remediation in the dirty tree, land with effectively zero static or coverage gating. The remediation itself left scar tissue (144 meaning-free VAL_N constants from a committed auto-fixer, 259 of 673 files carrying @file:Suppress, 133 mechanically named *Sections.kt files), and the dirty tree continues the suppress-rather-than-restructure pattern into security-critical crypto files. SwarmBackground.kt remains a 2,978-line single-class file with ~770 lines of generated coordinates whose generator script does not exist anywhere in the repo. Net verdict: code health is moderate and recoverable, but the lane's quality-control story is currently theater, and re-wiring the existing (already-built) gates is cheap, high-leverage, and should precede any new refactoring.

## q-backend (Code Quality & Maintainability)
This lane is substantially healthier than its framing suggests: all three TS backends compile with strict:true, functions/src contains exactly one `any` outside tests, error handling is consistently fail-closed with justified parse-fallback catches, and the repo already runs unusually mature debt tooling (knip, jscpd, syncpack, a TypeSpec schema-sync pipeline, hand-maintained-TS budgets, error-debt/type-debt counters). The real debt is gate rot rather than sloppy code: the functions lint gate has a shell-glob bug that silently skips every top-level src/*.ts file (16 real eslint errors hide behind a green check), the legacy-schema ratchet baseline is ~7x stale so it can never fail, and knip runs warn-only while two entire modules (insightAnalysis.ts, cloudSearchCore.ts) and 9 of 14 generated type files sit dead. The headline "legacy.ts god file" is an actively managed migration that stalled at stub level — generated types even shadow legacy names with drastically thinner shapes. The Python side (3,903-line adapter.py, byte-identically mirrored into the hermes-agent fork with a CI diff gate) is high quality but concentrates keychain, ICU-collation emulation, ECMA number formatting, replay ledger, ratchet, and an interactive wizard in one module with zero Python lint/type checking in CI. The single scariest correctness seam is PoP canonicalization depending on Node's `localeCompare` (ICU) being re-implemented in Python/Swift/Kotlin and pinned only by hand-copied inline vectors.

## q-web (Code Quality & Maintainability)
This lane (apps/console, website, extensions) is one of the healthiest corners of the repo: the console is strict-TS with zero `any`, typed callable contracts, codegen-synced domain registry, and Swift↔WebCrypto interop fixtures; the website has an unusually rigorous 17-gate verify chain (CSP hash fail-closed, copy-drift gates, reduced-motion/idle-loop/inline-budget tests); the extension has knip, replay fixtures, and full CI. The headline defect is severe, though: website/src/lib/firebaseClient.ts kept fake placeholder fallbacks that the console's mirrored module deliberately fixed, and because CI deploys with no env, the LIVE burnbar.ai bundle ships 'AIzaSyFakeKeyPlaceholderForBuild' today — sign-in on /link and /hermes/connect is broken in production and no gate can see it. The remaining debt is concentrated where the site's own gate pattern wasn't applied: mcp.astro inlines tool copy that has already drifted from the hosted-MCP registry (8 of 10 tools) under a comment claiming it never drifts, the iOS-consumed public/data/models.json is an ungated duplicate of the rundown seed, and four 1,500-2,400-line god-pages concentrate merge-collision risk. The console's one weak seam is the documented exportUserData polling workaround with an unchecked cast on the device-trust path, plus zero UI-flow tests. Verdict: high-quality lane with a small number of sharply-defined, mostly small-effort fixes — but one of them is a fix-today production breakage.

## a-desktop (Architecture & Design)
The macOS lane (AgentLens + OpenBurnBarCore + OpenBurnBarDaemon) has genuinely strong bones where it matters most: shared Codable contracts in Core are consumed symmetrically by app and daemon, the daemon is split into seven least-privilege executables, PrivilegedPeerAuthenticator does real audit-token code-signature validation, and a previously-tracked 2,102-line CloudSyncService god object has been honestly decomposed into a 230-line facade plus per-domain services — prior reviews here get acted on. The erosion is concentrated in three places: (1) the OpenBurnBarCore base target is a 289-file kitchen sink (66 SwiftUI view files, AppKit process-launching services, and vault crypto in one module) that the privileged daemon links wholesale; (2) the privileged-input path has accreted four wire shapes across three transports with silent fallback chains, and one committed app-side caller uses `try?` in a way that converts a hardened-lane rejection into a retry on the legacy lane; (3) the client app accumulates 2,500–4,400-line view/controller files and a second, app-embedded mission-execution engine that bypasses the daemon's MissionControl entirely. The dual SwiftPM+XcodeGen build definition of the daemon (with diverging dependency sets gated by canImport) is a quiet correctness hazard. Net verdict: boundaries are well-drawn on paper and at the security seams, but module granularity and the client layer are eroding faster than the existing reviews are retiring debt — most of the systemic items below are already named in DILIGENCE_REPORT_2026-06-10.md and remain open.

## a-ios (Architecture & Design)
OpenBurnBarMobile is a feature-rich, fast-moving iOS codebase with real architectural intent (the recent HermesRuntimeStore extraction, ThreadInboxStore aggregator, policy-enum reducers in the screen-share view show the team can cut good seams), but the service layer has not kept pace with feature growth. HermesService (3,270-line class, 59 commits since March) and FunctionsRepository (9+ unrelated backend domains including E2EE sealing crypto) are genuine god objects, and the documented "per-surface conversation state" rule is silently violated by at least four cross-cutting services that read/write HermesService.shared, producing latent user-visible defects today (permission pills and live gateway replies that never appear in the main chat). The view layer compensates for a missing controller tier with 24-closure prop-drilling chains and 14 files over 1,500 lines, and the whole app is one flat 546-file target glued by 62 singletons with no protocol seams at most store boundaries. None of this blocks shipping now, but doubling the feature surface under this structure would force the rewrite the 06-10 diligence report already predicts; the good news is the highest-leverage cuts (transport extraction, FunctionsRepository split, single-source-of-truth transcripts) are mechanical and have in-repo precedents to follow.

## a-android (Architecture & Design)
The Android lane is a six-week-old (first commit 2026-05), 871-file / 166k-LOC deliberate screen-by-screen port of the iOS app (docs/ANDROID_NATIVE_PARITY_GOAL.md is literally a prose spec of the iOS UI), and its debt profile follows directly from that: iOS ownership idioms were transplanted without an Android-native answer to lifecycle, so the app runs on four competing object regimes (ViewModels-in-the-data-package, .shared() singletons, global objects, Application companion statics) with no composition root, and its flagship stateful service (HermesService) is constructed per-screen and never destroyed. The crypto/protocol lanes are genuinely strong — AndroidKeyStore used correctly in 8 places, a cleanly extracted iroh-relay module, and fixture-based cross-language conformance for the Signal/relay/media seal formats — but that rigor is uneven (CloudVault AAD parity is prose-only, insight credentials sit in plaintext prefs). The celebrated detekt-zero of 2026-05-31 is partly mechanical (133 *Sections.kt files, 142 VAL_<n> constants, 270 file suppressions) and entirely unenforced because detekt is absent from CI, as are both Jacoco verification gates the build file defines. Net verdict: a remarkably complete port whose surface quality outruns its structural foundations; the next five features will hurt most wherever they need shared chat/connection state, a second app entry point, or a protocol change that must land on two platforms at once.

## a-backend (Architecture & Design)
This lane is healthier than its size suggests — 64 test files in functions/src, a real schema-sync/TypeSpec drift gate in CI, a canonical data-domains registry with rules driftcheck, automated deploy-firestore.yml, and a genuinely well-designed idempotent privacy-backfill migration arm. But the protective systems are thinner than they look: the entitlement/billing policy is forked across at least nine hand-maintained implementations (rules x3, two same-named-but-different functions in the functions package, hosted-mcp, the retired relay, Swift/Kotlin clients) with live drift that likely denies App Store Pro Max/Ultra purchasers Pro-level callables; the TypeSpec migration covers ~519 generated lines against a 3,261-line hand-maintained legacy.ts that defines 21 of the same doc types a second time, and the hand-mirror checker only validates one of thirteen domains via substring matching. The most security-critical component in the lane — the Hermes agent/gateway Python runtime including relay_e2ee — does not live in this repo at all; its provenance is pinned in a manifest whose commit differs from the hardcoded pin in the PR workflow, and the fail-closed verification script is wired only into a weekly job that cannot satisfy its preconditions. Verdict: strong mechanisms, incomplete enforcement; the top two findings are correctness/trust issues worth fixing before launch, the rest is structural debt that is currently being held at bay by tests rather than by boundaries.

## a-system (Architecture & Design)
The cross-platform contract story is bimodal: the crypto byte-contracts (signal envelope AAD, HPKE v3, control-seal, media AEAD) are genuinely protected by shared KAT fixtures consumed on Swift, Kotlin, and Node with a CI proof harness, and the data-domains/design-tokens codegen is real and adopted — but the headline "TypeSpec schema canon" is a façade: nothing ever compiles the 15 .tsp files (the emitter is hand-written TS/Swift/Kotlin template literals in a 1,586-line generate.mjs), the generated Swift module is imported by exactly one test file, the generated Kotlin package has zero consumers, and the canon has already drifted internally (UsageRollupDoc exists in .tsp but only in hand-written legacy.ts in reality). So in practice the schema layer is N parallel hand-written copies (TS legacy.ts 3,261 lines, Swift TokenUsage.swift, Kotlin TokenUsage.kt 781 lines) held together by 54 prose "mirrors the iOS" comments and a substring-matching hand-mirror check that covers 1 of 14 domains. The single worst architectural exposure is that the entire production Python leg of the protocol (gateway/crypto/relay_e2ee.py, hermes_cli, tui_gateway, plus their hostile test suites) exists in this monorepo only as orphaned __pycache__ bytecode — unversioned, un-CI'd — while the tracked 3,903-line adapter.py byte-locks against it via comments. Monorepo cohesion is otherwise decent (XcodeGen + SwiftPM + Gradle + 18 independent npm roots + Makefile glue, with strong debt-ratchet tooling), though `make test` swallows Android failures locally. The subsystem most likely to need a rewrite is the iOS Hermes/media layer (HermesService 4,907 / HermesTabView 4,537 / ScreenShareViewerView 4,512), followed by the daemon HTTP gateway monolith; the in-tree but CI-less crates/burnbar-remote engine telegraphs a planned remote-control re-platform.

## t-swift (Testing & Correctness)
This lane is substantially healthier than its headline numbers suggest: across ~147K test LOC the dominant style is genuinely behavioral — the HTTP gateway suite drives a real loopback server, quota tests use real temp-dir filesystems with URLProtocol stubbed at the correct seam, daemon mission-control tests assert replay-idempotency and deterministic ordering against real stores, and migration tests cover corruption/backup/restore plus a seeded legacy-DB upgrade. Quota math, crypto envelope sealing, and SQLite migration infrastructure all have real coverage; the quarantine system is managed by manifest and ADR rather than silent deletion, and the CI retry runner only retries classified XCTest hangs while failing fast on real failures. The debt is sharply concentrated in two places: the privileged-input/XPC trust layer has vacuous unit tests plus a never-run env-gated red-team suite — the exact gap that let the lane-killing LOCAL_PEERTOKEN bug merge green, and the dirty tree is adding 409 more untested lines there right now — and the diff-coverage gate's presence-based carve-outs exempt the daemon, mobile, and all view code from per-line evidence, neutralizing the lane's enforcement mechanism. Below those, a 140-occurrence wall-clock-sleep habit (worst: assertions racing a 50ms grace timer on 10ms margins) and four 4,600-5,900-line single-class god suites with shared global state are the main structural liabilities. Verdict: strong test authorship undermined by gate integrity and one critical blind spot on the most dangerous surface; fix the privileged-input lane and the coverage gate before anything else.

## t-android (Testing & Correctness)
The Android lane is a tale of two test suites. Where tests exist they are genuinely excellent — 1,023 JVM tests with zero @Ignore/sleeps, hostile-path crypto coverage (tamper rejection, AAD relocation binding, node-emitted KATs, sealed-fields tests that assert plaintext absence and graph-edge cloaking), cross-language conformance vectors frozen against Swift, and the full :app:testDebugUnitTest suite running in the required PR check. But everything that proves quality *quantitatively* is dead: both JaCoCo verification gates have zero callers (with contradictory 40%/60% thresholds and docs claiming enforcement), the Kotlin diff-coverage gate was removed from CI this week (commit 941faf698), detekt fails at HEAD and is wired into no workflow, and the entire 14-class instrumented/Compose suite has never executed because ANDROID_E2E_ENABLED is set at neither repo nor org level (verified via API). Above the well-tested data/crypto layer, the orchestration tier — 23 of 27 stores, all 3 ViewModels, the 1,065-line CLIAgentMissionDispatcher currently being modified by the security remediation — has no tests at all, and the only on-device proof of real libsignal-android behavior sits in the dead instrumented lane. Net verdict: green Android CI currently certifies compilation, formatting, and data-layer/crypto correctness — nothing else — and most of the gap is already named in the June diligence reports but not yet closed on main.

## t-backend (Testing & Correctness)
This lane is deep-but-lopsided: where tests exist they are unusually serious (374 emulator-backed rules assertions gating real deploys, libsignal ground-truth vectors in handler tests, Swift⇄web crypto interop fixtures, a 16-script content-guard chain for the website), but the execution wiring is full of holes that make green checks overstate reality. The two worst gaps are silent non-execution: the standalone firestore-rules-tests/ package — sole rules coverage for the computer-use and media-budget surfaces — runs in zero CI lanes while still being actively edited, and the services/ backends (E2EE relay, paid hosted-MCP) have 22 test files no workflow ever runs, with the relay deploy script skipping tests entirely. Around them sits a pattern of configured-but-unenforced controls (functions coverage thresholds never evaluated, ZAP DAST that cannot fail, self-skipping integration suites, a Jest-flag test script vitest rejects) that mirrors the coverage-gate-integrity finding already documented in the 06-11 diligence. Rules-test breadth covers roughly two-thirds of the 134-match-block rules surface, and the 4,598-line monolith that carries it is a single high-churn collision-prone file. Verdict: the correctness foundation is genuinely strong for this stage, but the lane needs a "does it actually execute in CI" audit more than it needs new tests — three of the highest-severity findings are one-day wiring fixes.

## t-ci-gates (Testing & Correctness)
This lane is a tale of two CI systems. The merge-blocking core (PR harness build/test jobs, gitleaks, rule0 supply-chain guard, firestore-rules tests in the functions lane, fast-feedback) is genuinely fail-closed and several previously-reported bypasses (rule0 gitlink, targeted-E2E silent-skip) are verifiably fixed. But every gate that measures *quality* rather than *compilation* is now theater or worse: the only diff-coverage gate was demonstrably gamed yesterday (presence-based carve-outs added 6 minutes after a 3.2%-vs-80% red run on the team's own privileged-input files, with Kotlin/TS coverage dropped from CI the same morning), the over-claim honesty gate is wired into zero workflows while another gate's comments claim it is enforced, the legal-approval release gate checks file existence instead of verifying signatures, nightly E2E is 10/10-red with DAST that cannot fail and issue-dedupe that mutes repeat failures, and a required branch-protection check has a silent-skip path that goes green having executed nothing. The pattern to fix is not individual scripts — it is that gates here are allowed to self-certify (skip green, warn-only, or accept presence as proof) the moment they become inconvenient.

## r-desktop (Reliability / Ops / Infra)
This lane is in genuinely good shape at its core — far better than the average always-on menu-bar app: the April fatalError-on-launch crash was replaced by a real startup-recovery flow with sidecar archiving, SQLite gets WAL + integrity-check + pre-migration backup/restore, the daemon binary is swapped atomically under launchd KeepAlive with heartbeat, exponential-backoff supervision, crash-loop detection, and protocol-version self-update, and both processes have structured os_log + Sentry with metadata sanitization. The debt concentrates almost entirely in the NEW privileged-input/remote-unlock lane, which has none of that maturity: the panic kill-switch's app-side activation writes to root-owned /var/run and silently fails in production (tests only exercise an env-override path, and the signed-off threat model claims SLOs this path cannot meet), the privileged-input helper is started via bare Process().run() with launchd supervision deliberately removed, and the XPC/socket client stack is a zero-logging, silently-falling-through, semaphore-blocking transport sandwich. Secondary, tracked debt: 25 empty catch blocks and 808 try? in app services (metrics stagnant against their own 30-day targets, including the exact "silently fail" keychain-save pattern the 2026-04-27 reliability review flagged), plus unrotated file logs and a cross-process SQLite coupling that B-DATA-1 encryption will break. Net: the legacy daemon plane is production-grade; the privileged-input plane is telegraphing that it needs the same supervision/observability treatment before launch.

## r-backend (Reliability / Ops / Infra)
The functions/ops lane has unusually good scaffolding for a pre-launch product — structured PII-scrubbed logging enforced by a CI verifier across all 49+ callables, cockatiel circuit breakers with a no-raw-fetch gate, documented fast (revision-pin) and slow (source) rollback paths, and health endpoints with a post-deploy gate. But the operational plane on top of that scaffolding is substantially non-functional today: the production deploy is wedged (deploy-production.yml still lacks the submodule checkout the preflight requires, so even post-counsel deploys will fail), Sentry for functions has never received a production event because no deploy path provisions SENTRY_DSN, every GCP alert routes to an undeliverable channel and the in-repo gate cannot detect that, and the scheduled verification lanes (ops-confidence, ops-plane-verify, nightly prod-health) are structurally red for reasons unrelated to outages — which, combined with title-prefix issue dedupe, suppresses detection of real failures. Three revenue-adjacent Cloud Run services deploy only from a laptop, and the auto-rollback "previous tag" logic silently broke when the versioning scheme switched to v1.0.2. Verdict: detection and deploy are the two weakest links; most fixes are hours, not weeks, but until the deploy wedge and alert path clear, production is effectively unmonitored and unfixable through the sanctioned lane.

## r-release (Reliability / Ops / Infra)
Artifact-level release engineering is genuinely strong — Developer ID signing, notarization+stapling, Sparkle-signed feeds, SBOM/VEX/cosign attestations, a fail-closed legal+provenance preflight, and a real DMG launch smoke — but the operational layer around it is brittle. The deploy plane is split-brained (hosting and Firestore rules auto-ship from main while functions ship only from v* tags and are currently wedged behind the legal hold plus the still-unfixed submodule-checkout bug), so production functions are 8 days stale with the known Stripe exploit live. Hosting auto-deploy on main push is, on balance, safe: it has concurrency serialization, trust-copy drift gates, a post-deploy smoke that demonstrably fails loud, and documented rollback — its residual risks are the unpinned firebase-tools and the issue-dedupe alert masking shared by all four alerting workflows. Rollback readiness is the weakest spot: the documented fallback (rollback.sh) would deploy a year-old beta with all runtime config missing because prod config exists only inside a workflow heredoc, and the fast path is per-service across ~144 functions. Versioning is fragmented across three tag schemes and four platform version namespaces with a CHANGELOG that no longer maps to tags, and the release runbook describes a prerelease-promotion safety model the workflow no longer implements. Most Critical-tier items are already on the 06-11 diligence ledger; the new findings here (rollback tag-sort/env-loss, straight-to-latest publishing, homebrew wrong-org, dispatch source-commit metadata) are cheap to fix and should ride the same remediation wave.

## s-deps (Security / Dependency / Compliance)
The supply-chain *architecture* here is well above startup norm — pinned vendor manifests with tree hashes (hermes-agent C-5), an allow-listed libsignal fork delta (M-6), SBOM+VEX cosign attestation, SHA-pinned core actions, and per-ecosystem deny tooling — but the *operational loop* behind it is broken. The single most damning number: zero of 80 Dependabot PRs have ever been merged in two months of operation, while 40 sit open including security-group bumps for the deployed relay and hosted-MCP services, and renovate.json is dead config the bot never executes. Scanning coverage is hand-enumerated and stale (2 of 16 npm lockfiles, one of two Rust workspaces, zero Python), and the release-time deny/attest workflow fails open when its tools aren't installed — which they aren't. The biggest blind spot is the Hermes gateway runtime: 113 .pyc files with no source, no Python dependency manifest, and a vendor-manifest/CI-gate pin skew, in the component the repo itself calls its most security-sensitive. Verdict: strong design, weak follow-through — most fixes are S-effort process/wiring changes (merge policy, recursive OSV, fail-closed deny checks, AAR hash gate, PR-time libsignal delta check) rather than new systems.

## s-backend (Security / Dependency / Compliance)
Access-control fundamentals in this lane are genuinely strong: centralized auth/App Check helpers that fail closed in production (functions/src/config.ts L-3 guard), a hardened PoP-v2 bearer scheme on the Hermes gateway, uid-scoped tenant isolation throughout hosted-mcp, and default-deny storage rules. The debt is structural rather than acute: firestore.rules is a 4,179-line hand-maintained monolith (123 functions, 116 match blocks) with systematic near-duplication and three hardcoded product-ID catalogs; entitlement gating is independently implemented in at least four places held coherent only by a dual-write convention; and the remote-MCP auth surface advertises an OAuth server that does not exist while minting refresh tokens nothing can redeem. Callable input validation is a competent but hand-rolled, per-callable convention (no schema layer), rate limiting is fragmented across five bespoke implementations, and the burnbarOperator super-claim has no minting/inventory tooling at all. None of this is launch-blocking on its own, but most of it is asymmetric-downside debt: one missed edit in a duplicated list or one rushed completion of the phantom OAuth flow becomes a real access-control bug. The active dirty-tree remediation (computerUseSecurity.ts +203, hermesGateway.ts +26) does not touch any of these seams.

## s-client (Security / Dependency / Compliance)
The keychain/keystore custody and entitlement posture is largely sound: iOS/macOS keychain items consistently use kSecAttrAccessibleWhenUnlockedThisDeviceOnly with no synchronizable flag, release entitlements carry no dangerous keys (no get-task-allow / disable-library-validation), the daemon HID helper is minimally entitled, and the HTTP gateway fails closed on missing auth tokens with a constant-time comparison. The serious debt is concentrated in the privileged-input transport: the dirty working tree is mid-migration from a launchd Mach service to a predictable, squattable /tmp Unix socket whose client performs zero server authentication on the path that types the plaintext macOS login password — a confirmed credential-capture lane already tracked as P0-6 in DILIGENCE_REPORT_2026-06-11.md, plus the proof (a wrong LOCAL_PEERTOKEN constant shipped at HEAD) that the privileged-peer gate has never been exercised live. Android is the weakest E2EE custody point: setUnlockedDeviceRequired is used nowhere, so the at-rest Signal private key, CloudVault key, and saved Remote Unlock passwords are wrapped by keystore keys usable while the device is locked, and one store's docstring overstates the protection it enforces. Hardened-runtime — which the peer gate requires on the app — is added only by an out-of-band signing script, not pinned in the build config. Net: a strong baseline undermined by one launch-blocking privileged-path regression in flight and a cross-platform Android custody gap.

## p-mac (Performance / Scalability / Data)
The UI/compute side of this lane is in unusually good shape: two documented perf sweeps (May + June 2026, docs/architecture/macos-performance.md §1-16) fixed SwiftUI invalidation, timer publishers, the popover rebuild, daemon RPC fan-out, and installed a DEBUG N+1 query tracer with self-calibrating budgets — and BackgroundCadenceCoordinator is a genuinely good canonical timer surface. The data plane underneath is where the real debt lives, and one item is on fire: `INSERT OR REPLACE` on conversations bypasses the FTS delete trigger (SQLite only fires delete triggers under REPLACE when recursive_triggers is ON, which it never is), so the founder's own live database has leaked 1.94M orphaned full-text copies — 11.5 GB of a 14.3 GB file that logically holds ~41 MB of conversation text, growing ~0.2-1 GB/day and being copied into 13 GB migration backups. Beneath that, the refresh pipeline still performs O(entire-history) work every 60-second tick (full reparse, full-table usage upsert, an N+1 SELECT-with-fullText per conversation, two fetchAllUsage full-table reads), and nothing bounds growth because the retention purge is a no-op stub, the backfill scheduler advances cursors without backfilling, completed projection jobs are never reaped (176k dead rows), and the daemon's controller-events journal appends forever (126 MB live). In short: pixels and timers were boiled clean, but the lifecycle of data — delete, compact, retain, increment — was never built, and the perf sweeps' gating (UsageReplaceGate, parser file-signature caches) currently masks a per-tick cost that grows linearly forever.

## p-mobile (Performance / Scalability / Data)
The mobile lane (OpenBurnBarMobile/ + android/) is in better shape than its size suggests: a serious cross-platform perf sweep (commits c12026c24, e23d0ac54, 365b4b485; PRs #301/#302) recently fixed asset bloat, listener fan-out, keyed transcripts, vsync caps, and off-main decodes, and media buffers (JitterBuffer, chunk assembler) are properly bounded. What remains is structural rather than incidental: per-frame video stats are plumbed straight into observable UI state on all three screen-share surfaces (whole-screen re-evaluation at frame rate), Android chat streaming still does per-token full-list rebuilds and full-text markdown re-parses while the deliberate 80ms commit throttle is only now landing on iOS in the uncommitted working tree, and the chat-history data model — one monolithic JSON file rewritten synchronously per turn plus one sealed Firestore doc per thread carrying the entire message array — degrades linearly with history and has a hard 1MiB-doc failure waiting. Add 4.5-4.9k-line god files with an unenforced SwiftLint file-length gate, and the lane's main risk is that chat and screen share — the flagship features — accumulate jank and a sync-breaking data ceiling precisely as real users build up history.

## p-backend (Performance / Scalability / Data)
This lane is bimodal: the recently remediated hot paths are genuinely strong engineering — the pending-delta queue with coalesced drain (crosscut-011), cursor-paginated full rebuild with a circuit breaker (P0-7), and the cursor-resumable quota-sweep backfill (crosscut-010) are well-documented, typed, and tested — but none of it is live (production functions are pinned at June 3 per DILIGENCE 06-11), and the structural cost ceilings underneath are untouched. The biggest unpriced liabilities are: zero Firestore TTL policies while at least six collections write expireAt/lease fields expecting one (including a PoP-nonce doc created on every authenticated gateway request and never deleted), a 36-composite cartesian index matrix on session_logs that simultaneously over-indexes an unused facet and misses the two facets the cockpit callable actually advertises, and a scheduled-worker fleet whose serial, fixed-batch design caps global throughput (50 rollup users/5min, 20 quota refreshes/15min) regardless of user count. The confirmed P0 migration-backup gate from the SOTA plan is verified FIXED in OpenBurnBarDatabase.swift (runMigrationsSafely with integrity check, pre-migration backup, restore-on-failure, and a self-healing latest-migration identifier replacing the stale hardcoded v45). Net: the team demonstrably knows how to fix these problems; the remaining debt is mostly known, registered, and shaped — the risk is that growth-rate items (TTL, index matrix, fan-out ceilings) are deprioritized because they only hurt at 10x.

## p-build (Performance / Scalability / Data)
Build and developer-experience health is the weakest layer of an otherwise heavily-engineered delivery system: the CI harness has grown sophisticated gates faster than it has grown a sane build substrate. The dominant pathology is that the libsignal Rust FFI is recompiled from scratch in up to eight macOS jobs per PR while the declared SPM caches restore directories the test scripts never read — and the team's observable response has been to raise timeout budgets four times since May rather than cache the artifact. Local setup is worse than CI: the publicly documented `make install` / QUICKSTART path cannot succeed on a fresh clone (uninitialized libsignal submodule, missing Rust/protoc prerequisites, a hardcoded signing team), which is a launch-week liability for an open-source AGPL repo whose positioning is verifiable trust. The filesystem-conditional Package.swift, the undocumented single-file-compilation workaround, and the tribal simulator-arch knowledge show a pattern of point fixes layered over an unstable build core instead of stabilizing it. The good news: the fixes are unusually cheap relative to payoff — one FFI-artifact job plus corrected cache paths, a `make bootstrap` target, and a verified QUICKSTART pass would remove the bulk of the pain in roughly a week of focused work. Gate-integrity issues (coverage carve-outs, qa.yml green-washing, nightly history) are real but already tracked in the 06-10/06-11 diligence reports; this lane's new findings are the cost and onboarding debt underneath those gates.

## gap-0 (Gap probe)
Code quality in this lane is substantially better than 'entirely unreviewed' predicted: the Python MCP server uses parameterized SQL with allowlisted columns and a sanitized DB path, resume_core spawns via argv arrays with 0600 briefings and validated session handles, mcp-remote is Keychain-first with honest leakage documentation in embed.ts, and all 95 tests across the three surfaces pass when run by hand. The debt is concentrated in the delivery system around the code, which is essentially absent — zero CI lanes run any of these suites, both Cloud Run services deploy laptop-only (quota-runner via a doc-embedded gcloud command with no test gate), and there is no Python lint/type-checking anywhere. That absence has already let a product-breaking defect ship on the paid hosted-MCP path: the advertised OAuth endpoints do not exist, access tokens expire in 15 minutes, and the refresh tokens the backend mints are discarded by every consumer, so the CLI works for one demo and then 401s forever. Secondary structural risks are the 8-way hand-duplicated CloudVault crypto constants whose 'MUST stay byte-identical' contracts are enforced by comments, the local MCP's documented plaintext-env-var handling of the E2EE vault key, and fail-open shared-secret auth around the quota-runner. Fixing this lane is cheap relative to its exposure: one CI workflow, two deploy scripts, a token-refresh path, and a cross-language KAT fixture cover the top findings.

## gap-1 (Gap probe)
This lane is the single worst unmitigated operational risk I have seen in this codebase, and it is live-verified, not inferred: production Firestore (projects/burnbar/databases/(default)) has PITR DISABLED, delete protection DISABLED, a 1-hour version retention window, zero backup schedules, and zero backups (gcloud, read-only, 2026-06-11), and all six Cloud Storage buckets have object versioning off with only the 7-day default soft delete. The repo contains no export automation, no IaC, and no restore runbook anywhere — the only mention of restoration is docs/runbooks/rollback-automation.md:137 prescribing "Roll back + restore from backup" for Firestore data corruption, a backup that does not exist. Meanwhile the same backend runs daily fleet-wide destructive automation (privacyBackfill scheduled FieldValue.delete sweep across 14 collections, recursiveDelete + force deleteFiles in deleteDomainData, panic drains, vault-wrapper removal in rotation), and the most critical data class — escrow vault-key wrappers in account_recovery_methods, the ONLY recovery path for E2EE-sealed data — is server-write-only with exactly one copy in the universe. The architecture has already accepted the fix (B-BE-1: PITR + scheduled exports + drill-tested restore runbook is named in docs/architecture/region-strategy.md as "the accepted outage-recovery mechanism for GA"), but it was never implemented, the SOTA plan that defined it is no longer in the tree, neither diligence report mentions backup/PITR at all, and no launch gate checks it. The good news: the headline fix is genuinely a one-day job (enable PITR + delete protection + a daily backup schedule + weekly export to a locked bucket + a restore runbook), and the local-first architecture means much usage/conversation data is re-derivable from healthy clients — but escrow wrappers, audit timelines, and entitlements are not.

## gap-2 (Gap probe)
The lane is healthier at the leaves than the probe hypothesis feared but hollow at the enforcement layer. The security-critical types I audited directly — OBBSignalProtocolStore (NSRecursiveLock, documented), FileCapabilityTokenNonceStore and the replay/nonce ledgers (locked), VirtualHIDKeyboardEngine (NSLock, currently being hardened in the dirty tree), PTYInteractiveSession and BurnBarResumeService (Locked/queue-confined), PhoneControl key stores (stateless keychain wrappers) — are mostly disciplined, and @MainActor+@unchecked-Sendable is used as a legitimate pre-Swift-6 idiom in the big controllers. But strict-concurrency 'complete' is essentially annotation-theater as a guarantee: Swift 5.10 language mode means even Xcode targets only get ignorable warnings with no warnings-as-errors, both SwiftPM packages (E2EE crypto + privileged daemon) carry zero swiftSettings so every CI lane and the shipped release daemon binary build with minimal checking, and there is no ThreadSanitizer lane anywhere. Meanwhile @unchecked Sendable grew 26→173 in under a month with only 9 AUDIT comments, and the worst verified cluster is real: nine CloudSync domain services share a copy-pasted unguarded isSyncing check-then-act race across suspension points, aggregated by a non-MainActor @Observable coordinator and defeated entirely by a second legacy orchestration path. The worst three concrete unsafe types are ConversationSyncService, SessionLogSyncService, and CloudSyncCoordinator, with a latent ratchet-fork race in the not-yet-wired OBBSignalSessionCipherTransport as the highest-stakes time bomb.

## gap-3 (Gap probe)
The probe's premise is fully confirmed and then some: across all five user surfaces there is zero localization scaffolding — no String Catalog or .strings file on any Apple target (0 NSLocalizedString calls against 2,235 hardcoded Text literals in 311 files), a single Android values/ dir whose strings.xml holds only 7 framework-required strings (0 stringResource calls against ~490 inline Compose literals in 120 files), and hardcoded lang="en" with no i18n routing on both the Astro site and the Next.js console. No review doc, diligence report, ADR, wiki page, or commit records English-only as a decision, even though the team demonstrably knows the pattern (their upstream hermes-agent contributions sit next to a fully i18n'd en/ja/zh/zh-hant desktop app, and RemoteUnlockBlockerPresentationMap proves they can do copy-as-data). The debt is concentrated in exactly the god files already slated for decomposition, so the decision window is now: an ADR plus a near-free String Catalog and lint ratchet captures most of the option value at M effort, while deferring it means re-touching ProjectsView/HermesTabView-class files twice. One piece bites today regardless of posture: Android's four ad-hoc currency formatters mix a hardcoded "$" with default-locale number formatting, rendering "$12,34" on comma-decimal devices and disagreeing with the Mac/iOS rendering of the same number. Verdict: not a launch blocker, but an unmade architectural decision with a closing window — record it or cut the seam before the refactors land.
## r-mobile (Reliability / Ops / Infra)
The push backend in functions/ is the strongest part of this lane (idempotent state machines, backoff, stuck-push sweepers, dead-lettering — production-grade). Everything in front of it is operationally dark: iOS ships zero crash reporting (Sentry linked, never started), Android Crashlytics is permanently off behind a preference nothing writes, and Android 13+ users never see a notification because POST_NOTIFICATIONS is never requested and every posting path swallows the SecurityException. Net: feature-complete but ops-blind — if mobile breaks in the field, the team finds out from store reviews, not telemetry.
