# Linux account authentication authority

## Scope

Linux account sign-in is a daemon-owned device-code flow. The React renderer
may start, display, poll, cancel, and sign out through typed local RPCs, but it
never receives a device secret, delivery private key, Firebase custom token,
ID token, or refresh token. Local SQLite remains authoritative for local
product data whether the user is signed in or not.

This authority implements the source-level in-app sign-in/sign-out foundation
of `LNX-AUTH-001`. It does not certify a deployed browser-to-daemon flow,
native Linux App Check attestation for protected cloud operations, live Secret
Service/KWallet behavior, cloud sync,
trusted-device management, or the complete billing/restore matrix.

## Authority layers

| Layer | Responsibility |
|---|---|
| Website | Authenticate the approving user, obtain web App Check, bind the App Check claim, consume a single-use high-risk nonce, and approve the exact requested purpose. |
| Cloud Functions | Own the transient device-link record, enforce purpose and expiry, mint a short-lived Firebase custom token for `request.auth.uid`, and seal it to the Linux delivery key. |
| Swift daemon | Own the device secret, P-256 private key, Firebase token exchange, refresh lifecycle, profile cache, secure persistence, cancellation, and sign-out. |
| Rust shell | Proxy typed account RPCs and open only the validated BurnBar approval URL in the system browser. |
| React renderer | Present redacted account state and schedule non-overlapping polls using the daemon-provided interval and expiry. |

## Local RPC contract

The daemon exposes five capability-scoped methods:

| Method | Result |
|---|---|
| `daemon.account.status` | Redacted account snapshot. |
| `daemon.account.device_auth.start` | Pending snapshot with opaque flow id, user code, approval URL, expiry, and poll interval. |
| `daemon.account.device_auth.poll` | Pending, signed-in, or signed-out-with-problem snapshot for the requested flow id. |
| `daemon.account.device_auth.cancel` | Idempotently cancels the requested pending flow and clears in-memory delivery material. |
| `daemon.account.sign_out` | On successful durable credential deletion, idempotently clears the pending flow, in-memory Firebase session, and locally stored refresh token; deletion failure preserves the signed-in session. |

The renderer-visible state enum is deliberately small:
`signed_out`, `authorization_pending`, and `signed_in`. Recoverable storage,
network, reauthentication, and expiry conditions use a typed `problem` object
without lying about the last authoritative account state.

## Credential delivery

Desktop auth uses a protocol separate from Remote MCP credential delivery:

- Algorithm: `p256-ecdh-aes-256-gcm-v2`.
- Key context: `OpenBurnBar desktop auth credential delivery v2`.
- AAD: `openburnbar:desktop-auth:credential-delivery:v2:<flow-id>`.
- The flow id is a canonical UUID generated by the daemon and persisted only
  as non-secret link metadata.
- The encrypted payload is schema-versioned and must declare both
  `desktop_auth` and `firebase_custom_token` before the daemon exchanges it.

The Functions document stores no plaintext credential: its credential field is
only a sealed envelope, alongside bounded non-secret link metadata and the
device-secret verifier. Polling also requires proof of the device secret, and
only the daemon-held P-256 private key can open the envelope. Remote MCP keeps
its v1 context and cannot be substituted into a desktop-auth flow.

## Secret custody and failure semantics

Before opening the browser, the daemon verifies that an approved writable
SecretStore backend is healthy. Desktop writes are allowed only through an
unlocked Secret Service or KWallet backend. Headless systemd credentials remain
read-only inputs and are not treated as a writable session store. No plaintext
file or environment fallback is accepted for a newly issued refresh token.

The daemon persists a received or rotated refresh token before publishing the
session as signed in. ID tokens and delivery material stay in memory. A locked
keyring, network outage, expired approval, invalid grant, malformed envelope,
wrong flow, or tampered ciphertext returns a typed recoverable problem and does
not silently enable cloud behavior.

A non-secret backend-affinity marker is written to the selected keyring before
the refresh token. Restore, writable preflight, rotation, and deletion honor
that same backend. Sign-out retains the marker as a signed-out tombstone, so a
stale token in another configured keyring cannot revive the session. Legacy
credentials establish affinity before use or deletion, and repeated deletion
does not call a native backend for an already absent token.

Every token-bearing device-auth, Firebase identity, and membership request uses
a no-redirect session. HTTP redirects are refused, and a response is accepted
only when its final URL exactly matches the requested endpoint.

Ordinary sign-out matches Firebase client semantics: it clears the local
session without calling the Admin SDK user-wide refresh-token revocation API,
which would sign the user out on every device. Local SQLite data is not deleted.

## Website approval sequence

The approval page performs this order:

1. Initialize reCAPTCHA Enterprise App Check before the callable request.
2. Authenticate the user with Google or Apple.
3. Call `bindAppCheckAttestation`.
4. force-refresh the Firebase ID token so the bound claim is present.
5. Call `issueHighRiskActionNonce`.
6. Call `completeCliLink` with the normalized user code, exact expected
   `desktop_auth` purpose, and single-use nonce.

Unknown purposes and purpose mismatches fail before credential issuance.
Desktop auth does not require a Pro entitlement and cannot enter the Remote MCP
grant path.

## QA matrix

1. Start from signed out with an unlocked Secret Service backend. Verify one
   pending flow, one browser window, bounded polling, successful approval, an
   immediate signed-in profile, and no secret in renderer/Tauri payloads.
2. Repeat with KWallet as the only writable backend.
3. Lock or remove the keyring before start. Verify the browser does not open and
   the UI reports `secret_store_unavailable` with repair guidance.
4. Exercise cancel, expiry, wrong flow id, wrong device secret, offline polling,
   late poll completion, and retry. Exercise a server-seeded `denied` response
   as protocol compatibility; there is no user-facing decline action yet.
   Exactly one flow and one poll request may be active.
5. Tamper with the envelope algorithm, AAD, public key, IV, tag, ciphertext, and
   payload discriminants. Every case must fail without persisting a token.
6. Restart after sign-in. Verify refresh-token recovery from Secret Service or
   KWallet, refresh rotation before use, and profile recovery without exposing
   the token.
7. Sign out twice. Verify both calls succeed, local SQLite remains present, and
   the refresh token is no longer readable. Inject keyring deletion failure and
   verify the current session remains signed in and restart-restorable until a
   later deletion succeeds.
8. Seed a stale token in a secondary keyring. Verify storage, preflight,
   rotation, sign-out, repeated sign-out, and restart remain bound to the
   authoritative backend even when the secondary backend fails deletion.
9. Return 301, 302, 307, and 308 from every token-bearing endpoint and return a
   200 response with a different final URL. Verify no redirected request is sent
   and every mismatched response is rejected.
10. Inspect logs, diagnostics, process arguments, environment, renderer DOM,
   local storage, and captured IPC. No device secret or Firebase credential may
   appear.

## Remaining parity blockers

- Production `mintLinuxAppCheckToken` still has no real Linux attestation
  verifier and intentionally fails closed outside non-production fixtures
  (`LNX-APPCHECK-001`).
- Membership checkout/restore still requires a correct Linux-safe endpoint and
  App Check contract; Apple JWS restore is not a Linux substitute
  (`LNX-MEMBERSHIP-001`).
- Cloud backup/conflict sync and trusted-device lifecycle remain separate
  `GAP-010` work (`LNX-SYNC-001` and `LNX-DEVICE-001`).
- Exact-candidate GNOME, KDE, and headless runtime certification remains
  required before `LNX-AUTH-DEPLOY-001` can be accepted or promotion can occur.
