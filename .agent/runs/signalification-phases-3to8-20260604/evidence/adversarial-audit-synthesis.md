## 2. Prioritized confirmed findings + fixes

### Highest priority (activation-gate, fix before flipping any flag)

**A. Stream 6 trust UI shows the server-stored-fingerprint safety code; the key-bound verifier is dead code (major).**
The shipping safety codes (`MacTrustedDevice.safetyCode`, `DeviceRecord.safetyCode`) derive from the server-supplied fingerprint *string*, not the public-key bytes. Neither model carries `publicKeyData`, so the correct key-bound verifier (`EscrowDeviceSafetyCode.isFingerprint(_:boundTo:)`, fully tested, 18/18) is never invoked. A fully-compromised server can advertise a self-consistent but spoofed fingerprint, and the only anti-spoof control (the client key-bound display) is unwired. Reachable the moment the Stream 6 flag flips.
*Fix:* add `publicKeyData: String?` to both device models; populate from `escrow_public_keys/{deviceId}_{keyVersion}.publicKeyData`; change both `safetyCode` computeds to `format(publicKeyData:)`; gate the Approve button on `isFingerprint(fingerprint, boundTo: publicKeyData) == true`; flip both flags together. Keep behind the flag.

**B. Server escrow fingerprint recompute lacks P-256 curve-membership validation that native CryptoKit enforces (minor).**
`recomputeEscrowFingerprint` (computerUseSecurity.ts:91-101) checks only length 65 / `0x04` prefix / base64 round-trip — an off-curve `0x04 + 64×0xAB` blob hashes and is accepted, while CryptoKit's `P256.KeyAgreement.PublicKey(x963Representation:)` rejects it (reproduced empirically). Same gap exists in `parsePublicKeyJwk` (webAppCheck.ts), so an off-curve key can be *stored* via the supported `registerBrowserEscrowDevice` callable. Breaks the intended byte-for-byte server↔Swift parity at flag-ON.
*Fix:* after the length/prefix checks, `crypto.createPublicKey({key:{kty:"EC",crv:"P-256",x,y},format:"jwk"})` in a try/catch → return null on failure; mirror in `parsePublicKeyJwk`; add the off-curve negative test to `escrowDeviceTrustFingerprint.test.ts`. Additive, flag-OFF-safe.

**C. `bindingToAAD` canonicalizer diverges from its own spec `SIGNAL_ENVELOPE_V1.md §5.4` (minor).**
The spec mandates *reusing* legacy AAD grammar (`OpenBurnBar-CloudVault-aad-v2|…`, `OpenBurnBar-HermesRelay-v1|…`) with an `OpenBurnBar-Signal-AtRest-v1|` info prefix; the implemented code emits a fresh `OpenBurnBar-Signal-AAD-v1|` + `[mode,scope,uid,clientId,collection,docId,field,slotId,formatVersion]` grammar, dropping `schemaVersion/purpose`. The load-bearing anti-tamper string disagrees between spec and code.
*Fix (preferred):* update the spec (§5.4, the worked example at line 280, the phantom `OpenBurnBar-Signal-AtRest-v1|` references, and Open-Questions Q5/Q9/Q11) to the implemented grammar — code+fixtures are byte-parity-proven and are the source of truth. Resolve the "reuse legacy labels" open question explicitly as "fresh v4 namespace, no cross-version oracle."

**D. v4 binding canonicalizer applies no Unicode (NFC) normalization in TS or Swift (minor).**
Non-NFC-stable segment bytes (e.g. `é` as NFD vs NFC) would diverge cross-platform and fail-close a cross-language v4 open. Inert today (all live segments are ASCII; no production seal caller).
*Fix:* normalize each segment to NFC before the join in the single shared serializer on both sides (`s.normalize('NFC')` / `.precomposedStringWithCanonicalMapping`); add a non-ASCII NFD-vs-NFC byte-parity vector and an NFD→NFC round-trip test. Must land before the Stream 3/5 flag is enabled.
