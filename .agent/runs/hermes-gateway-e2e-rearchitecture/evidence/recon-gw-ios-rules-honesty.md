# Recon notes (key facts that drive the design)

**Asymmetry of the two gateway directions** — there are two server-written paths, written from two different identities, so sealing must happen at two different code points:
- **iOS → agent** ("events"): `enqueueHermesGatewayEvent` callable (`functions/src/callables/hermesGateway.ts:1100-1201`). iOS sends plaintext `text`/`senderDisplayName`; server writes `users/{uid}/hermes_gateway_events/{eventId}`. iOS is the producer → **iOS seals**, server stores ciphertext, the agent (key-holder) opens.
- **agent → iOS** ("messages"/"attachments"): bearer-token HTTP `handleMessageSend` (`:473-501`) + `handleAttachmentInit` (`:599-647`). The **agent** (Hermes fork adapter) is the producer → **agent seals** (that is PR2's slice), iOS opens.
- The agent's existing write-back HTTP path `handleRuntimeStatus` (`:523-561`) is exactly where the agent already merges fields into its own `hermes_gateway_clients/{id}` doc — the natural place for the agent to **publish its relay pubkey** (mirrors `pi_agent` `relayPublicKey` at `functions/src/types/legacy.ts:213,727`).

**iOS relay-seal precedent is already in the tree.** `HermesService.swift:3836-3883` and `:4180-4230` already do `HermesRelayCrypto.sealToBase64` + `wrapSymmetricKey(recipientPublicKeyBase64:)` against a host's `relayPublicKey`, writing `payloadCiphertext`/`wrappedKey`/`relayKeyVersion`. `FunctionsRepository.swift:1282-1306` already plumbs `relayPublicKey`/`relayKeyVersion`/`relayEncryption` through `completePiAgentPairing`. The gateway should reuse this verbatim — only the AAD namespace and the key-publish location differ.

**iOS as a key endpoint needs its own persistent relay private key.** Today only the *host* (Mac/Pi) holds a relay private key; iOS only ever wraps to a host pubkey. For the gateway, iOS is the producer for events **and** the recipient for messages, so iOS must hold a persistent P-256 relay keypair (Keychain, `…WhenUnlockedThisDeviceOnly`, same pattern as `iOSDeviceKeypair.swift:101-152`) and publish its pubkey at pairing.

**`relayPublicKey` already reaches the iOS client decode path? No — must be added.** `HermesGatewayClientDoc` (`legacy.ts:592-610`) and `publicClientView` (`functions/src/hermesGateway.ts:523-547`) and the iOS `HermesGatewayClientRecord` (`FunctionsRepository.swift:88-211`) all lack `relayPublicKey`. All three must add it so iOS can wrap event keys to the agent.

**Migration tooling already half-covers the gateway.** The operator scrubber (`scrub-chat-cloud-plaintext.mjs:101-112`) already lists `hermes_gateway_messages/events/attachments` — but it deletes **unconditionally** (correct for an incident scrub). The in-product idempotent backfill (`privacyBackfill.ts:73-149`) does **not** list the gateway collections, and its safe pattern is "delete only when `requires` sealed field present." The gateway must be added there with the sealed gates.

## DESIGN BRIEF

### A. iOS relay key endpoint (new file)

1. **Create `OpenBurnBarMobile/Services/HermesGatewayRelayKeypair.swift`** — a Keychain-backed persistent P-256 relay keypair for the phone, modeled byte-for-byte on `OpenBurnBarMobile/Services/iOSDeviceKeypair.swift:101-152` (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, service `"com.openburnbar.mobile.hermes-gateway-relay"`). Expose:
   - `static func loadOrCreate() -> HermesGatewayRelayKeypair` (P-256 `KeyAgreement.PrivateKey`).
   - `var relayPublicKeyBase64: String` → `privateKey.publicKey.x963Representation.base64EncodedString()` (65-byte X9.63, matches `HermesRelayCrypto` recipient format at `HermesRelayCrypto.swift:128`).
   - `var privateKey: HermesRelayPrivateKey` (wrap via `HermesRelayPrivateKey(rawRepresentation:)` — note `HermesRelayPrivateKey` already exists in `HermesRelayCrypto.swift`).
   - `let keyVersion = HermesRelayCrypto.keyVersion`.
   Do **not** invent crypto here; this file only persists the key and hands it to `HermesRelayCrypto`.

2. **Define gateway AAD helpers** (add to `HermesGatewayRelayKeypair.swift` or a small extension on `HermesRelayCrypto`). Reuse the existing `HermesRelayCrypto.aad`/`keyWrapSharedInfo` design by namespacing: bind `uid|clientId|eventOrMessageId|kind`. Concretely add:
   - `static func gatewayEventAAD(uid:clientId:eventId:) -> Data` and `gatewayEventKeyAAD(...)`, and `gatewayMessageAAD(...)`/`gatewayMessageKeyAAD(...)`, each delegating to the private `HermesRelayCrypto.aad([...])` form (prefix `"OpenBurnBar-HermesRelay-v1|"` is preserved; the parts list is `["gateway-event", uid, clientId, eventId]` etc.). If `aad`/`keyWrapSharedInfo` are `private`, add thin `public static` wrappers in `HermesRelayCrypto.swift` rather than duplicating the string — keep the single source of the prefix.

### B. Publish the phone relay pubkey at pairing (iOS + repository + server)

3. **`OpenBurnBarMobile/Services/FunctionsRepository.swift:1150-1172`** (`approveHermesGatewayDeviceGrant` impl) — add `relayPublicKey` / `relayKeyVersion` / `relayEncryption` to the callable `payload` (only when non-empty), mirroring the `completePiAgentPairing` plumbing at `:1304-1306`. Source the values from `HermesGatewayRelayKeypair.loadOrCreate()`.

4. **Extend the protocol + default extension** at `FunctionsRepository.swift:656-702` (`approveHermesGatewayDeviceGrant` signature) and the call site in `HermesGatewaySettingsStore.approve` (`HermesSettingsView.swift:2252-2278`) so the phone pubkey is passed through. The store should call `HermesGatewayRelayKeypair.loadOrCreate().relayPublicKeyBase64` and pass it down.

5. **Server `approveHermesGatewayDeviceGrant`** (`functions/src/callables/hermesGateway.ts:873-966`) — accept `relayPublicKey?`/`relayKeyVersion?`/`relayEncryption?` in the request type (`:882-887`), validate (`relayEncryption === "p256-hkdf-sha256-aesgcm"`, `relayPublicKey` base64 of 65 bytes, `relayKeyVersion` int 1–100 — reuse the validation shape used for `pi_agent` at the completePiAgentPairing callable), and persist them onto `clientDoc` (`:927-940`). This is the phone's pubkey stored on the **client** doc so the agent can seal `messages` back to the phone, and the phone can confirm its own published key.

6. **Add `relayPublicKey`/`relayKeyVersion`/`relayEncryption` to `HermesGatewayClientDoc`** (`functions/src/types/legacy.ts:592-610`) and surface them in `publicClientView` (`functions/src/hermesGateway.ts:523-547`) so the iOS client-record decode can read the **agent's** published key (see C7) and the phone's own key. Update `isHermesGatewayClientDoc` type guard if it strictly validates keys.

7. **Agent publishes ITS relay pubkey via `handleRuntimeStatus`** (`functions/src/callables/hermesGateway.ts:523-561`) — accept `body.relayPublicKey`/`relayKeyVersion`/`relayEncryption`, validate them the same way, and merge them onto the client doc in the `db.doc(...).set(stripUndefinedObject({...}), {merge:true})` block (`:537-551`). (The Hermes-fork adapter sending these is PR2; this is the BurnBar-side server contract that receives them.) Result: `hermes_gateway_clients/{id}` carries the **agent's** pubkey (for iOS→agent event sealing) and the **phone's** pubkey (for agent→iOS message sealing).

### C. iOS seal-on-send (events) + open-on-receive (messages)

8. **`HermesGatewayClientRecord` decode** (`FunctionsRepository.swift:88-211` struct, `:145-168` Codable init, `:213-…` Firestore `init?(documentID:data:)`) — add `relayPublicKey: String?`, `relayKeyVersion: Int?`, `relayEncryption: String?` (the **agent's** key). These are what iOS wraps event keys to. Add a computed `var canSealToAgent: Bool { relayEncryption == HermesRelayCrypto.algorithm && (relayPublicKey?.isEmpty == false) }` (mirrors `HermesService.swift:3585`).

9. **Seal events in the repository** at `FunctionsRepository.swift:1185-1231` (both `enqueueHermesGatewayEvent` and `enqueueHermesGatewayModelSwitch`). Change the signatures (protocol `:666-680`, default ext `:708-736`, impl `:1185-1231`) to accept the target client's `relayPublicKey`/`relayKeyVersion` (or pass the whole `HermesGatewayClientRecord`). Inside the impl, BEFORE building `payload`:
   - Generate a per-event symmetric key: `let key = try HermesRelayCrypto.generateSymmetricKeyData()`.
   - `let eventId = UUID()`/client-chosen id used in AAD (send it as the doc id so the AAD binds; OR derive AAD from server-assigned id — simpler: have iOS pass a client-generated `eventId` that the server honors).
   - Seal the JSON `{text, senderDisplayName, modelId?}` payload: `payloadCiphertext = try HermesRelayCrypto.sealToBase64(plaintext: payloadJSON, keyData: key, aad: gatewayEventAAD(...))`.
   - Wrap to the agent: `wrappedKey = try HermesRelayCrypto.wrapSymmetricKey(key, recipientPublicKeyBase64: client.relayPublicKey!, aad: gatewayEventKeyAAD(...))`.
   - Replace the plaintext keys in `payload` (`:1193-1199`, `:1216-1224`): **drop** `text`/`senderDisplayName`/`modelId`, **add** `payloadCiphertext`, `wrappedKey`, `relayEncryption: HermesRelayCrypto.algorithm`, `relayKeyVersion`, `eventId`. Keep `destinationId`/`threadId`/`senderId`/`targetClientId`/`eventKind` plaintext (routing-only, non-PII; `senderId` is `"burnbar-ios"` constant).
   - **Legacy fallback:** if `client.canSealToAgent == false` (un-upgraded agent with no published pubkey), keep sending plaintext `text`/`senderDisplayName` so pairing still works mid-migration, and surface a notice. Gate this behind a `requireSealedGateway` build flag defaulting on once the fleet is upgraded.

10. **Server `enqueueHermesGatewayEvent`** (`functions/src/callables/hermesGateway.ts:1100-1201`) — accept `payloadCiphertext`/`wrappedKey`/`relayEncryption`/`relayKeyVersion`/`eventId` in the request type (`:1109-1119`). When present: **reject** any plaintext `text`/`senderDisplayName`/`modelId` (HttpsError invalid-argument), validate the envelope (relayEncryption equals the algorithm constant, base64 shapes), and write the sealed fields to `hermes_gateway_events/{eventId}` (`:1170-1187`) INSTEAD OF `text`/`senderDisplayName`. Keep `sequence`/`destinationId`/`targetClientId`/`threadId`/`senderId`/`kind`/`createdAt` plaintext. Bump `HERMES_GATEWAY_SCHEMA_VERSION` (so old plaintext docs are fenced by version; see migration). The model-switch case still needs a routable model id — store `modelId` only as a **server-keyed match token** or carry it inside the sealed payload and have the agent validate against its catalog (it already does, `:1145-1152`); since the model-availability check at `:1145-1152` runs server-side, move that authority entirely to the agent and drop the server-side `clientAdvertisesModel` gate when sealed (note this as an accepted behavior change).

11. **iOS open-on-receive (messages)** — `HermesGatewayMessageRecord` (`FunctionsRepository.swift:504-547`) and its decode `init?(documentID:data:)` (`:516-534`): add `payloadCiphertext`/`wrappedKey`/`relayEncryption`/`relayKeyVersion` fields. Add an async/throwing `decodedText(using keypair:)` that, when sealed fields are present: `key = unwrapSymmetricKey(wrappedKey, privateKey: phoneRelayPrivateKey, aad: gatewayMessageKeyAAD(...))` then `plaintext = openBase64(payloadCiphertext, keyData: key, aad: gatewayMessageAAD(...))`, returning the decoded `text`. **Legacy fallback:** if sealed fields absent, return the existing plaintext `text` (`:530`). Because decode now needs the keypair + can throw, do the open in the snapshot handler (next item), not in the value-type init.

12. **`handleMessagesSnapshot`** (`HermesSettingsView.swift:2487-2529`) — after building `messages`, map each record through `record.decodedText(using: HermesGatewayRelayKeypair.loadOrCreate())` (await; do it in the `Task { @MainActor }` that already wraps the handler). Store the opened plaintext on the in-memory record (add a `resolvedText` field or a parallel `[id: String]` map) so the resolver (`HermesGatewayMessageResolver.newestThreadReply`, `FunctionsRepository.swift:576-586`, which checks `message.text?.isEmpty == false`) and the render path use the opened text. **`presentReplyNotification`** (`:2542-2552`) must use the opened text, not `reply.text` (which is now ciphertext-absent).

13. **Render path** (`HermesSettingsView.swift:2235-2273`, the reply view that shows `latestReply`) — read the opened/resolved text rather than the raw `text` field. If open fails (key mismatch / un-upgraded agent), show a graceful "Reply is sealed for another device" state instead of empty.

14. **Attachments (agent→iOS)** — the agent seals the attachment bytes (PR2) and stores `sealedFileName` on the manifest. iOS side: when the manifest decode (currently `attachmentIds` only on the message record, `:512`/`:531`) surfaces a filename, read `sealedFilename` (CloudVaultSealedText via the relay key, or vault `sealText`) with a legacy `fileName` fallback. For THIS slice, the iOS change is: tolerate a missing plaintext `fileName` and open `sealedFilename` when present; full attachment-body open is in PR2.
