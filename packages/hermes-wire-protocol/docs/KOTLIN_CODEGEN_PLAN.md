# Kotlin generate-and-consume — design & staged plan

> Grounded design from the design+drift workflow (7 agents, ~670k tokens). Implements the deferred half of G9: make the Android Kotlin relay payload types schema-generated so Swift<->Kotlin drift is structurally impossible.

**Recommendation:** hybrid

## Rationale
Schema-driven Kotlin codegen is the correct structural fix and is feasible, but a single load-bearing adversary blocker is REAL and confirmed by direct evidence, so a pure mechanical "emit and consume" would regress the encode wire shape. The blocker: Swift emits 18 non-optional defaulted fields UNCONDITIONALLY, while the current hand-written Kotlin (HermesRealtimeRelayFrame.kt:1343-1348 `encodeDefaults=false`) with @EncodeDefault on only 2 fields (protocolVersion :28, callKind :551) DROPS 16 of them at default. I verified this with a script over the schema honoring the actual Swift encode-synthesis rule (a struct gets a custom encode ONLY if a field declares codable.encode — relay-types.mjs:137; otherwise Swift synthesizes encode and emits ALL stored properties). The 18 always-emitted defaulted fields: Frame.protocolVersion; RemoteUnlockCapabilities.{supportedBackends,supportedLockStates,blockers,allowsCredentialPaste,allowsSavedCredentialUnlock,fileVaultSSHSupported}; AgentTerminalRequest.interactive; DisplayDescriptor.isPrimary; CallInvite.callKind; VideoCodecCapability.{lowLatencyEncode,temporalLayering,longTermReference,screenContentCoding} (verified synthesized encode at Generated/HermesRealtimeRelayMedia.swift:665-714 — custom init(from:) only, NO encode(to:)); MediaFrameVersionSupport.{supportsV1,supportsV2} (:716-735); StreamingCapabilities.{mediaFrameVersions,videoDatagrams}. This is a PRE-EXISTING Swift->wire vs Kotlin->wire asymmetry that exists at HEAD (masked because both decoders tolerate absence via decodeIfPresent ?? default / ifPresentDefault, and no cross-platform test asserts Kotlin-bytes==Swift-bytes for these). A faithful generate-and-consume that mirrors Swift's wire would FIX this (emit @EncodeDefault on all 18), but that is a wire CHANGE for 16 fields, so it must be a deliberate, prover-gated decision rather than a silent side effect. The other confirmed blockers (dualKey PresenceHeartbeat field-topology divergence; 3 missing enum cases that cause live decode crashes AND break a non-exhaustive consumer `when`; 3 date-regime type flips with live producer/consumer arithmetic coupling) all require coordinated consumer edits in the same change. Therefore: generate the ~52 mechanically-safe types from the schema (full codegen for those), special-case the 1 dualKey type (PresenceHeartbeat) with a generated custom KSerializer, and sequence the genuine drift fixes (enums, dates, @EncodeDefault breadth) as deliberate prover-gated migrations with their consumer edits landed atomically. Defer nothing — everything is completable here with gradle — but stage it so each step is independently verifiable and no step regresses the parity vectors. The encode-mode-as-wire-type-selector rule (NOT decode-mode) is correct and load-bearing: I confirmed MirrorStop.stoppedAt and MirrorDisplaySelection.selectedAt have decode.mode=dateIso but encode.mode=plain, so Swift encodes a NUMBER (Generated/HermesRealtimeRelayMedia.swift, schema verified) and Kotlin Double (Frame.kt:531,541) is CORRECT — a decode-mode-keyed emitter would wrongly flip these to String.

## Round-trip prover
Mirror migrate/roundtrip.mjs (the Swift byte-faithfulness precedent that parses hand-written Swift, re-emits, and per-type semanticMatch-diffs — verified at packages/hermes-wire-protocol/migrate/roundtrip.mjs:286-291,370-384). Build packages/hermes-wire-protocol/migrate/kotlin-roundtrip.mjs that: (1) PARSES the current hand-written android/.../HermesRealtimeRelayFrame.kt into a per-type model (data classes, enums, @SerialName, defaults, @EncodeDefault, field types) using the same brace-matched top-level splitter + member segmentation approach as roundtrip.mjs:23-77. (2) For each schema type, RE-EMITS via the new emitKotlinRelayTypes and NORMALIZES both (drop comments/whitespace, sort nothing semantic) then asserts equality PER TYPE — exactly migrate/roundtrip.mjs's semanticMatch. (3) The diff IS the zero-regression objective: for the ~52 mechanically-identical types the prover must report FAITHFUL (generated == current hand-written, normalized) BEFORE the generated file replaces the hand-written declarations. (4) For the KNOWN-DRIFT types (the 8) the prover EXPECTS a difference and asserts the difference equals the intended FIX (e.g. lastChangedAt: current Double -> generated String; backend enum: current 5 cases -> generated 6) via an allowlist of expected-diffs, so an UNEXPECTED diff still fails. This separates "faithful reproduction" (must hold for everything Kotlin already gets right) from "intended fix" (must hold for the 8). Run: `node packages/hermes-wire-protocol/migrate/kotlin-roundtrip.mjs` reports `faithful: N/52` and `intended-fix: 8/8`. Complement with a gradle-side ENCODE-BYTE prover (new HermesRealtimeRelayGeneratedRoundTripTest.kt in the iroh-relay module test dir) that, for each type, constructs an all-defaults instance, encodes via HermesRealtimeRelayJson, and asserts the emitted key SET == the Swift-emitted key set (every unconditional default present, every nil-optional absent) — this is what structurally forces the @EncodeDefault scope to be correct, which the existing decode-only presence_heartbeat test (IrohRelayFrameCodecTest.kt) cannot catch.

## Risks
1. @EncodeDefault breadth is a real wire CHANGE for 16 fields (verified 18 always-emitted, 2 already @EncodeDefault). If any production decoder ANYWHERE treats presence-vs-absence as meaningful (it should not, given ifPresentDefault tolerance, but unverified across all 115 consumers), turning these on could change observed behavior. Mitigate with the encode-byte prover + a staged flag; conservatively this single fix can be preserve+flag.
2. PresenceHeartbeat dualKey is the one type where schema topology (1 field, both-keys-encode) != current Kotlin (2 fields displayName+deviceDisplayName, no fallback). Generating a class-level KSerializer that emits both keys CHANGES the wire (current Kotlin emits each key only when its field is set) AND requires preserving a `displayName` constructor alias for 7 call sites (MediaControlPresence.kt:47-48, MediaControlStreamCoordinatorInbound.kt:116-117, 5 tests). Safest fallback: keep PresenceHeartbeat hand-written (excluded from generation) like the other behavior types — but then it remains a drift surface the prover must still walk.
3. Swift Generated relay types are NOT currently in any CI git-diff drift gate (confirmed: only packages/hermes-wire-protocol/gen + the TS file are diff-checked). The Swift side could already be silently stale; adding the Kotlin gate should also close this Swift gap or the 'drift impossible' claim is only half-true.
4. u64 fields (AuthorityEnvelope.counter, LongTermReferenceAck.tokenValue) map to signed Kotlin Long; values > 2^63-1 would overflow kotlinx decode. Pre-existing, masked by monotonic counters under 2^63. Keep Long for source-compat; document, do not silently switch to ULong.
5. ktlint runs over src/**/*.kt (build.gradle.kts:78); generated output must be ktlint-clean or excluded or the module build red-fails — easy to miss until :openburnbar-iroh-relay assemble.
6. The intent-hash/F10-seal-AAD must be proven byte-identical across the date-type flips and unaffected by FrameType.wireValue (Frame.kt:937 reads serializer descriptor at runtime); the relay emitter must NOT regenerate FrameType/wireValue. A regression here silently breaks control-frame auth, not just JSON shape — add the explicit resign test.
7. Sequencing matters: landing the enum/date fixes WITHOUT the atomic consumer edits red-builds :app (non-exhaustive when at PhoneControlSignerJsonEncoding.kt:81; Double arithmetic at SystemPermissionConcierge.kt:88). Each phase must compile :app before merge.
