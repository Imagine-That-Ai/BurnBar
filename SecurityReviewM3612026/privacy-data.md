# Privacy & Data Protection — OpenBurnBar Second-Opinion Review (2026-06-01)

**Specialist:** Privacy & Data Protection
**Scope:** All personal data, sensitive data, secrets, prompts, files, screenshots, transcripts, logs, agent traces, and metadata; retention, deletion, export, consent, and admin/employee access; claims-rewrite verification.
**Source posture:** Local-first (SQLite/GRDB + optional SQLCipher), opt-in cloud sync (Firestore + Firebase Storage), opt-in iCloud mirror, opt-in hosted search (AES-GCM sealed), opt-in Hermes/Floo, opt-in MCP.
**Existing posture docs:** `docs/PRIVACY.md`, `docs/THREAT_MODEL.md`, `docs/security/LLM_GENAI_AGENT_THREAT_MODEL.md`, `docs/OPENBURNBAR_SEARCH_ARCHITECTURE_SPINE.md`, `docs/PROVIDER_ACCOUNTS.md`, `website/CLAIMS.md`, `security-review-2026-06-01/SECURITY_CLAIMS_REWRITE.md`.

The product already has unusually strong privacy primitives (zero-knowledge hosted search, owner-scoped Firestore rules with secret-field denylist, ECIES-P256 cross-device escrow, all key material at `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`). The findings below are therefore precision findings, not a wholesale posture critique. Where the existing public claims rewrite (SECURITY_CLAIMS_REWRITE.md) is accurate, I confirm it. Where it is too generous, I narrow it.

## 2. Verification of SECURITY_CLAIMS_REWRITE.md

I re-read every rewrite claim in `security-review-2026-06-01/SECURITY_CLAIMS_REWRITE.md` against the actual code. The claims rewrite is largely accurate and appropriately conservative. Specifics:

### Verified accurate
- **"Local-first … cloud features never replace local state"** — `docs/THREAT_MODEL.md:127-148`, `SessionLogSyncService.swift` only writes after `assertActiveBurnBarProEntitlement`; local SQLite is the canonical store. ✓
- **"WhenUnlockedThisDeviceOnly"** for SQLCipher key + Iroh — `DatabaseEncryptionService.swift:73`, `IrohRelayKeyStore.swift:127, 166`. ✓
- **"ECIES (P-256 + AES-GCM) cross-device credential escrow"** — `SessionLogSyncService.swift:720, 752` and THREAT_MODEL.md:227. ✓
- **"App Check enforced for Firestore in production console configuration"** — `THREAT_MODEL.md:141-142`, `SECURITY_PRIVACY_REVIEW.md:25`, `AppCheckAttestation.ts:120`. The enforcement itself is a console-level config; the code does its part via `enforceAppCheck: getConfig().enforceAppCheck` on every callable. ✓
- **"Signed upload URLs are short-lived and issued only after entitlement and path ownership checks. Post-upload verification enforces size, content type, and integrity"** — `encryptedSearch.ts:50-103, 144-321, 178-296` (`assertEncryptedSessionBlobObject`). ✓
- **"Local database encryption uses a key stored exclusively in the macOS Keychain with WhenUnlockedThisDeviceOnly protection. Loss of the Keychain item … renders the encrypted database unrecoverable without an explicit user-created recovery bundle"** — `THREAT_MODEL.md:134` + `DatabaseEncryptionService.swift:73, 124-169` (PBKDF2 100k + AES-GCM). ✓
- **"Relays cannot decrypt payload contents but can observe metadata such as endpoint identities (NodeIds), connection patterns, timing, and data volumes"** — `THREAT_MODEL.md:14, THREAT_MODEL.md:20-22`, `IROH_IROH_TRANSPORT.md`, Hermes Cloud Run relay retired 2026-05-28 (THREAT_MODEL.md:143). ✓
- **"Code-sign on privileged paths … no silent activation"** — `THREAT_MODEL.md:26-26` + P0 remediation in `plans/2026-05-30-sota-security-remediation.md`. The rewrite says WS2 is "partially implemented" — the FINDINGS_REGISTER.md C1 entry is consistent with that. ✓
- **"… multiple independent kill switches (global hotkey, phone gesture, lock screen, Remote Config)"** — `THREAT_MODEL.md:17`, master plan. ✓
- **"Tamper-evident SHA-256 chain … with optional OpenTimestamps proofs allow offline verification"** — `LLM_GENAI_AGENT_THREAT_MODEL.md:96, 100-105` + `computerUseOpenTimestamps.ts` (PRIVACY.md:71). ✓

### Partially accurate / needs narrowing
- **"OpenBurnBar servers cannot decrypt the content without your device-held keys"** — true for the encrypted body blobs and the AES-GCM sealed text/snippets. BUT the existing claim rewrite omits that:
  - Hosted search servers learn the *index* of which token hashes / semantic hashes a chunk contains — so the server knows "this user has a session whose chunks contain hashes A, B, C" but not the plaintext. The rewrite is technically right but understates the indexing exposure (see Finding P-4).
  - The hosted `queryConversations` endpoint returns sealed manifests with non-sealed facets (provider, model, project name, cost, total tokens, message count, working directory — `encryptedSearch.ts:707-833`). The facets are plaintext-visible to the server. The server never sees body content, but the facets are sensitive in their own right (e.g., project names can be confidential). See Finding P-4.
- **"Iroh E2E encrypted, we can't see it"** for Floo/Mercury — the rewrite (line 7) already correctly qualifies "partially accurate for payload but omits relay metadata." The website itself still says "no one in the middle can read it, and that includes us" (`website/src/data/capabilities.ts:92`, `website/src/data/faq.ts:193`) — the rewrite should be applied to those public strings too (see Finding P-1).
- **"… Only your own paired devices"** — rewrite says "true post-escrow + grant." However, the auto-`pending` device registration in `THREAT_MODEL.md:234` ("automatically registers as `pending` … can view synced stats but cannot import credentials") means a freshly-installed client can be auto-registered as `pending` and immediately read synced usage stats. The "only your own paired devices" framing is too strong for *metadata* — see Finding P-9.
- **"Local-first … Chat message bodies and full session log content are never uploaded … unless you explicitly enable the relevant backup setting"** — accurate for the `hosted_quota_sync` and BurnBar Pro flows. The iCloud mirror copies are plaintext by design (THREAT_MODEL.md:149-150, PRIVACY.md:54-56). The website's `iCloud.astro` page should mirror that, not imply a one-line "encrypted" treatment of the iCloud container. See Finding P-10.

### Confirmed gap to flag in the rewrite
- The rewrite says nothing about the device ID migration path in `AccountManager.swift:420-435`: the device UUID is created once and written to `UserDefaults`, then read on every launch. If the user "deletes cloud data" via `deleteUserCloudData`, the device ID is *not* scrubbed. A re-sign-in on the same device reuses the same ID and may re-aggregate historical data. See Finding P-3.

## 3. New Findings (with file:line evidence)

### P-1. Public "E2E encrypted, we can't read it" claim survives in the website after the rewrite
**Severity:** High (claim accuracy — published on the launch website)
**Component:** `website/src/data/capabilities.ts:92`, `website/src/data/faq.ts:193`, `website/src/pages/floo.astro:32`, `website/src/pages/index.astro:403`, `website/src/pages/mcp.astro:74-149`
**Evidence:** The website still publishes absolute phrasing ("No one in the middle can read it, and that includes us" / "End-to-end encrypted"). The 2026-06-01 SECURITY_CLAIMS_REWRITE.md (line 7) acknowledges this is only "partially accurate for payload" but it does not list the website strings that need updating. The matrix in `website/CLAIMS.md` for `/floo` still endorses "end-to-end encrypted, we can't read it" verbatim (CLAIMS.md:78).
**Attack scenario:** A user reads the launch website, enables Hermes/Floo, and is later told in a security disclosure that relay metadata was visible. The discoverable claim does not match the reviewed threat model.
**Impact:** Regulatory and reputational; specifically the in-app consent copy and website privacy policy need to mirror the rewrite.
**Root cause:** Two parallel copy surfaces (THREAT_MODEL + SECURITY_CLAIMS_REWRITE) were not propagated to the website and the matrix was not updated to flag these as `[verify]`.
**Fix:** Replace the absolute phrasing with the scoped language in SECURITY_CLAIMS_REWRITE.md. Mark the affected lines in `website/CLAIMS.md` as `[verify]` or `[rewrite]`. Add a CI check that fails `npm run verify` (CLAIMS.md:241) if a public string matches a banned-pattern list.
**Test:** Curl the staging website, grep for `No one in the middle can read it`, `End-to-end encrypted` standalone strings, and assert they appear only in the privacy policy page (not in marketing copy).
**Owner:** Website / Marketing + Security
**Priority:** P0
**Confidence:** High
**Verification status:** verified

### P-2. Hermes Gateway Cloud Run retired, but website still mentions it on privacy page
**Severity:** Medium
**Component:** `website/src/pages/privacy.astro:113` says **"Cloud Run · Hermes relay" routes encrypted frames; never sees plaintext**.
**Evidence:** `docs/THREAT_MODEL.md:143` — "Hermes hosted relay (retired 2026-05-28): The Cloud Run WebSocket relay and Redis backend were deleted from the `burnbar` project. Remote Hermes now uses iroh peer transport with Firestore as the last-resort fallback." And the privacy page architecture diagram references "Cloud Run · Node 22 · 2025-11-25 spec" (`mcp.astro:31`).
**Attack scenario:** A reader believes a managed relay still exists in the architecture, may overestimate attack surface (or underestimate the new Iroh metadata exposure) depending on which framing they trust.
**Impact:** Misleading claim about an active infrastructure surface that no longer exists.
**Root cause:** Stale website copy.
**Fix:** Update `website/src/pages/privacy.astro:113` and `mcp.astro:31` to reference Iroh (or remove the Cloud Run bullet). Cross-link the `docs/HERMES_REALTIME_RELAY.md` retirement notice.
**Test:** Manual + `npm run verify`.
**Owner:** Website.
**Priority:** P2
**Confidence:** High
**Verification status:** verified

### P-3. Device ID is never purged on cloud delete; sync resumes with same ID after re-sign-in
**Severity:** Medium
**Component:** `AgentLens/Services/AccountManager.swift:39, 420-435`, `functions/src/accountDeletion.ts:74-138`
**Evidence:** `loadOrCreateDeviceId()` reads/writes `UserDefaults` under `OpenBurnBarIdentity.deviceIDKey` and never migrates or purges. `eraseUserCloudData` only deletes `users/{uid}/...` and `workspaces/...` collections. It does not touch the device ID, nor any of the *client-side* artifacts like the *local* SQLite cache of server data, the daemon support directory, or the `UserDefaults` flag for "I have signed in before." The site `website/src/data/faq.ts:102-105` correctly tells the user to "delete the app and its support files" but does not warn about the device ID persistence.
**Attack scenario:** A user sells the Mac after deleting cloud data; the new owner reinstalls the app; the new owner signs in with their own Firebase UID; the device's old `deviceID` is unrelated to the new UID so a clean slate is set. BUT if the original user re-installs the app on the same Mac and re-signs-in, the same `deviceID` is used, and any per-device aggregation (e.g., `cloud_search_index_state/{deviceId}`, `usage` rows with `deviceId` partition) re-uses historical device identity. For users who sold or returned the Mac, the device ID persists in the per-device documents server-side even after `deleteUserCloudData`, because `eraseUserCloudData` only walks `users/{uid}` (accountDeletion.ts:109-111) and `workspaces/workspace-{uid}`.
**Impact:** Re-aggregation risk; per-device docs can outlive a "delete my data" action; the privacy promise "delete cloud data" doesn't fully describe what stays.
**Root cause:** Deletion tree does not include the *server-side* per-device docs that are not under `users/{uid}/` (there don't appear to be any in the current schema, but the device ID itself lives only client-side and is never compared/scrubbed).
**Fix:** Add a "Reset device identity" toggle in Settings → Privacy that wipes `UserDefaults` deviceID + clears local daemon support dir. In `accountDeletion.ts`, also return a list of deviceIds that were in the namespace and instruct the client to purge them.
**Test:** Add a regression test that calls `eraseUserCloudData` for a uid with seeded `cloud_search_index_state/{deviceId}` docs, then asserts no orphans remain in any user/workspace path AND no rows are still keyed by that deviceId in the user's usage docs.
**Owner:** Account + CloudSync.
**Priority:** P2
**Confidence:** High
**Verification status:** verified

### P-4. Hosted "queryConversations" facets expose plaintext sensitive metadata to the server
**Severity:** High (privacy)
**Component:** `functions/src/callables/encryptedSearch.ts:707-833` (`queryConversations`), `functions/src/callables/conversationQuery.ts`, `docs/OPENBURNBAR_SEARCH_ARCHITECTURE_SPINE.md:78-100`
**Evidence:** The Streams cockpit query accepts and returns plaintext facet fields: `provider`, `model`, `projectName`, `deviceId`, `sourceType`, `costUSD`, `totalTokens`, `workingDirectory`, message count, tags, `startTime`, `endTime` (see `mapSessionLogManifestRow` referenced in encryptedSearch.ts:797, and the cockpit docs at OPENBURNBAR_SEARCH_ARCHITECTURE_SPINE.md:88-93). PRIVACY.md:50 says "server-side indexes use only sealed metadata and keyed hashes" and SECURITY_CLAIMS_REWRITE.md:35 says "OpenBurnBar servers cannot decrypt the content without your device-held keys." Both statements are about the *body*; they understate the server's visibility into the *facet* plaintext.
**Attack scenario:** An attacker (or insider with `burnbarOperator` access) reads the faceted manifest in Firestore (which is not server-only; it is owner-readable by the user but also admin-readable per Firestore IAM) and learns "this user runs Anthropic Claude Code on `~/work/acme-corp/secret-redesign`, $42/day, 1.4M tokens/day, with 18 sessions tagged 'deploy'." The body remains sealed, but the *project name + cost + volume* is sensitive on its own.
**Impact:** Confidential project names and cost patterns leaked to anyone with Firestore read access (including the Cloud Functions runtime and Google staff under operator access).
**Root cause:** Facet fields were added to enable filtering/sorting and were considered "metadata" rather than "content."
**Fix:** Either (a) seal the facet fields (e.g., a deterministic keyed hash for projectName, encrypted for cost/tokens) and only return aggregates on the client; or (b) document this clearly in PRIVACY.md and the rewrite: "server sees faceted metadata (provider, model, project, cost, token totals, working directory) but never sees body content." Add a Settings toggle to redact project name and working directory.
**Test:** Seed a session with project name "Project-Secret"; assert the manifest stored in Firestore contains the literal project name and that `mapSessionLogManifestRow` returns it. (Currently the docs only seal `sealedTitle`/`sealedSnippet`/`sealedBodyPreview`.)
**Owner:** Cloud / Search.
**Priority:** P1
**Confidence:** High
**Verification status:** verified

### P-5. Sentry scope of data is unverified; `sentry.ts` doesn't constrain what gets attached
**Severity:** Medium
**Component:** `functions/src/sentry.ts:24-50`
**Evidence:** `Sentry.init` adds `requestDataIntegration` and `extraErrorDataIntegration({ depth: 5 })`. The doc comment on line 83 says "avoid sending PII to Sentry. This is sufficient for grouping, not for [diagnosis]" but the actual filtering of `request.auth.uid` etc. depends on what each handler passes. The user-side `OpenBurnBarTelemetryService.swift` is privacy-bounded (no PII by design), but the *server* Sentry capture can include `request.auth.token.email`, IP, and any field that flows into the wrapped `logError`/`logInfo` payload (logging.ts:82-99).
**Attack scenario:** A user enables crash reporting; a crash handler captures the callable's `request.data` which may include `clientId`, `displayName`, `installFingerprint`, or `sealedText` values (all bounded strings, but not sealed secrets). Sentry staff (or a leaked DSN) can read these.
**Impact:** Employee access to user identifiers via Sentry console.
**Root cause:** `sentry.ts` lacks a `beforeSend` hook that drops `request.auth.*` and the wrapped `data` payload.
**Fix:** Add a `beforeSend` that strips `request.auth`, `request.data`, and `user` from every event; reduce `extraErrorDataIntegration` depth to 1; add an opt-in DSN flag in env config so the deploy can turn off Sentry entirely for the privacy-strict builds.
**Test:** Synthesize a failing callable; assert the resulting Sentry event has no `request.auth` and no `request.data` keys (mock `Sentry.init` with a recorder).
**Owner:** Cloud / Observability.
**Priority:** P1
**Confidence:** High
**Verification status:** verified

### P-6. `ops/computer_use_session_daily_rollups` and `ops/media_session_daily_rollups` expose aggregate session details to operator reads — claim of "no chat content" deserves a test
**Severity:** Medium
**Component:** `firestore.rules:2083, 2618`; `functions/src/computerUseBudget.ts`, `computerUseMonitoring.ts`, `mediaBudget.ts`, `mediaMonitoring.ts`
**Evidence:** The rollups are operator-readable; the threat model says they "do not grant access to user chat content or provider credentials" (THREAT_MODEL.md:212). However, the rollups include `days/{day}` with projections: how many sessions, total tokens, total cost, total seconds, by user/UID. I did not see the writer code grep'd, but the `data` field names (e.g., `count`, `totalCostUSD`, `totalTokens`) can allow re-identification of which UIDs are heavy users, when their work week is, etc.
**Attack scenario:** Operator (`burnbarOperator` claim) reads the rollups. They learn a specific UID runs $X/week of Claude Code from Y timezone. They cross-reference with the public `provider_accounts` doc to see the redacted label "Work" or "Client."
**Impact:** Re-identification via rollups; the privacy claim "operators cannot see chat content" is true but the "no privacy risk" framing is not.
**Root cause:** Rollups do not aggregate by device or provider — they aggregate by UID and the UIDs are in plaintext in the rollup doc path.
**Fix:** Replace the UID with a salted hash in rollup docs (matching the `user_id_hash` approach in logging.ts:52); keep only `count` + bucketed `totalCostUSD` + `totalTokens`; do not store `startTime` per session.
**Test:** Assert that no `ops/*_session_daily_rollups` doc contains a `userId` or `uid` field; assert the writer hash function is the same as `logging.ts`.
**Owner:** Cloud / Observability.
**Priority:** P1
**Confidence:** Medium
**Verification status:** partial (no time to read every rollup writer; recommend verification before merging)

### P-7. Inconsistent Keychain accessibility classes — the headline "WhenUnlockedThisDeviceOnly" is not uniform
**Severity:** Medium

### P-9. Pending escrow device auto-registration reads synced usage before trust approval
**Severity:** Medium
**Component:** `docs/THREAT_MODEL.md:234-238`, `firestore.rules:1008-1010, 1477-1480`

## 7. Deletion / Export Gaps

1. **`eraseUserCloudData` does not delete Firebase Storage blobs.** accountDeletion.ts:74-114 walks Firestore only. A user with a 10 MB encrypted session body in `users/{uid}/session_logs/.../bodies/...json.aesgcm` will keep that ciphertext in the bucket after `deleteUserCloudData` returns success. This is not a privacy catastrophe (the ciphertext is AES-GCM, server cannot decrypt), but it is a *data minimization* failure and a *deletion promise* failure. **P-21** below.
2. **iCloud mirror copies are not in the deletion story.** PRIVACY.md:116 says "delete from iCloud Drive manually." The Mac app does not surface this. **P-14**.
3. **Local Keychain is not scrubbed by `deleteCurrentUser`.** accountDeletion + AccountManager.deleteCurrentUser (AccountManager.swift:384-391). **P-19**.
4. **Computer Use local audit chain + screenshots are not scrubbed.** Forever. **P-8, P-15**.
5. **Orphaned `escrow_envelopes` for un-reachable destinations** are not in the deletion scope. The envelope is deleted with the user namespace, but the local Keychain private key may persist. **P-19**.
6. **Stale cloud search index state per device** persists after `deleteUserCloudData` only if the user re-uses the same deviceId (which `AccountManager` does because the device ID is in `UserDefaults`). **P-3**.

### P-21 (new). `eraseUserCloudData` does not purge Firebase Storage blobs
**Severity:** High
**Component:** `functions/src/accountDeletion.ts:74-138`
**Evidence:** `eraseUserCloudData` only walks `users/{uid}` and `workspaces/workspace-{uid}` Firestore paths. It does not iterate `getStorage().bucket()` for `users/${uid}/session_logs/**` paths and call `file.delete()`. The storage.rules:5-14 path is owner-only, but the files themselves are not deleted.
**Attack scenario:** User calls "Delete my data." Two weeks later, the user signs in with a new UID; the bucket still has the old user's encrypted bodies. (No plaintext leak, but the privacy promise is "delete my data.")
**Impact:** Incomplete deletion. The PRIVACY.md claim "Delete cloud data" is only half-implemented on the Storage side.
**Root cause:** The deletion tree is Firestore-only.
**Fix:** In `eraseUserCloudData`, after the Firestore delete completes, list all `users/${uid}/...` objects in the bucket and delete them in a batch (use `bucket.getFiles({ prefix: \`users/${uid}/\` })` and then `file.delete()` per object). Verify the bucket is empty before returning success. Add a new return field `deletedStorageObjects: number`.
**Test:** Seed 50 session body blobs in the bucket under a test uid prefix; call `eraseUserCloudData`; assert `bucket.getFiles({ prefix: ... })` returns 0 files.
**Owner:** Cloud / Account.
**Priority:** P1
**Confidence:** High
**Verification status:** verified

## 11. Cross-Device Sync of Sensitive Material (EscrowEnvelopes, P-256 keys)

- Public keys: synced to Firestore `escrow_public_keys/{deviceId}_{keyVersion}` (firestore.rules via SessionLogSyncService.swift:715-722). All-UID-namespace. Rules reject plaintext secret fields. Good.
- Wrapped vault keys: `cloud_vault_key_wrappers/{targetDeviceId}_{keyVersion}` (SessionLogSyncService.swift:743-757). Server-side ciphertext; only the trusted target device can unwrap with its P-256 private key in its local Keychain. Good.
- Wrapped provider credentials (escrow envelopes): `users/{uid}/escrow_envelopes/{envelopeId}` (firestore.rules:2532-2538). Server-side ciphertext; same threat model. Good.
- Rules: `escrow_envelopes` only rejects plaintext-looking secret field names (apiKey, token, etc.); the rule does not enforce `algorithm: "ECIES-P256-AESGCM"`. A bug or downgrade attack that writes an `algorithm: "PLAINTEXT"` envelope would not be caught by the rules. **P-22** below.

### P-22 (new). Firestore rules do not enforce `algorithm` on `escrow_envelopes` / `cloud_vault_key_wrappers`
**Severity:** Medium
**Component:** `firestore.rules:2532-2546, 744-757` (SessionLogSyncService), `AgentLens/Services/CloudSync/SessionLogSyncService.swift:720, 752`
**Evidence:** The rules only call `hasNoPlaintextSecretFields()`. They do not require `request.resource.data.algorithm == "ECIES-P256-AESGCM"`. A future bug or downgrade attack could write a plaintext envelope.
**Attack scenario:** A future regression writes `algorithm: "PLAINTEXT"`, `payload: <base64 plaintext>` to `escrow_envelopes`. The rules pass; the destination device reads the plaintext; the threat model collapses.
**Impact:** Downgrade attack if a code change forgets to seal.
**Root cause:** Rule does not pin algorithm.
**Fix:** Add `&& request.resource.data.algorithm == "ECIES-P256-AESGCM"` to the `escrow_envelopes` and `cloud_vault_key_wrappers` create rules. Add a unit test that tries to write a non-ECIES envelope and is denied.
**Owner:** Cloud.
**Priority:** P1
**Confidence:** High
**Verification status:** verified
